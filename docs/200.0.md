## 1. Bug / 正确性 / 安全

### P0（致命 / 高）

**B-01 未分页 `.get()` 静默截断（单日 >100 单触发；机械清扫，非对账级事故）**
- 位置：`wxcloud/functions/lunch_order/index.js:824-828`、`1273-1277`
- 证据：`db.collection(COL.ORDERS).where({...}).orderBy(...).get()` 没有 `limit`，云函数端默认只返回 100 条；同文件 `:92-103` 的 `fetchAll` 已用 `limit(1000)` 分页。
- 影响：单日确认订单 >100 时，供应商视图和导出 CSV 静默少单。内部点餐更现实的触发点是个人菜品统计 >100（只影响"最近点过"排序），不是对账级事故。
- 同类截断：`:760-763`（取消申请）、`:858-862 / 874-878 / 901-905`（月度统计多年数据）、`lunch_menu/index.js:932-934`（个人菜品统计 >100）、`lunch_order/index.js:1757-1772`（`getUserMenuStats`，原误引为 `lunch_menu/index.js:1764-1766`）、`:314-316`（加组列表）。
- 修复：统一改用 `fetchAll`/`limit(1000)` 分页；补一条 >100 截断的回归用例即可，不必视为 P0 事故。

> B-02（原"getInitData 自动入组越权"）经确认属于产品允许的开放入组规则，不作为问题。以下编号保留原有序号，便于引用。

**B-03 今日日期时区不一致（仅设备时区非东八区时触发，降级为小改动）**
- 位置：`src/utils/date.ts:1-4` vs `src/hooks/useOrder.ts:179`
- 证据：`getTodayString()` 用 `d.getFullYear()/getMonth()/getDate()`（设备本地时区）；下单用 `new Date(Date.now()+8*3600000).toISOString().slice(0,10)`（北京时间）。
- 影响：仅当设备时区非东八区（出国、系统时区改动）时，今日订单列表、首页统计、管理页待办、批量确认错乱，而截止时间判断仍按北京时间。
- 修复：统一为北京时间工具函数（如 `getTodayString()` 内部同样 `+8h` 后取 UTC），并补跨时区单测。

> B-04（原"H5 端无法运行"）经确认本项目只配置 mp、不考虑 H5，不作为问题。以下编号保留原有序号，便于引用。

**B-05 语音配额检查非原子 / 异常 fail-open（P1；降级理由经二次核实修正）**
- 位置：`wxcloud/functions/lunch_voice/index.js:16-59`、`148-164`
- 证据：配额先 `doc().get()` 再 `_.inc(1)` 或 `set`，非原子；配额更新失败仅 `console.warn` 后仍 `return true`。
- 影响：并发请求可同时通过 `count<30` 检查造成超额；配额表异常即全放行。关于 `!openid` 放行：**复核发现 `lunch_voice` 的 `main`（:148-164）并没有 401 拦截**（401 只在 order/menu/backup 的 main 里），且 `rateLimit`/`checkDailyQuota` 遇空 openid 均直接放行；`config.json` 无 HTTP 触发器，纯小程序客户端路径下 OPENID 正常注入，故实际可利用性低，但与"main 已拦截"无关。云函数互调或控制台测试等场景仍可能出现空 OPENID 并计费，因此保留防御性修复。
- 修复：在 `lunch_voice.main` 先补 `if (!OPENID) return 401`；配额改为条件原子更新 `where({ _id: docId, count: _.lt(30) }).update({ data: { count: _.inc(1) } })`，首次无文档（更新命中 0）时改用 `set({ count: 1 })` 并容忍并发首建重复写，或用事务；更新失败改为 fail-closed。另建议给 `_rateMap` 补容量清理（与 `lunch_backup` 的 >10000 回收一致）。

**B-06 FlashRecognition 超时后仍双次计费**
- 位置：`lunch_voice/index.js:98-128`
- 证据：`Promise.race([flashPromise, timeoutP])` 只放弃等待，不取消已发出的腾讯云请求；超时后继续调用 `SentenceRecognition`；1000ms 定时器未 `clearTimeout`。
- 影响：超时场景每次识别产生 2 次 ASR 计费，且定时器堆积。
- 修复：拿到结果后 `clearTimeout`；超时后**不再立刻发 Sentence，直接返回"请重试"**，避免双计费。

**B-07 每周定时备份串行遍历所有组织，存在 20 秒超时导致漏备（最可信运维风险）**
- 位置：`wxcloud/functions/lunch_backup/index.js:349-363`；配置见 `lunch_backup/config.json`（timeout 20、租约 120s）
- 证据：`while(true)` 分页取组织后，逐个 `await runForGroup({action:'backupAuto'})`，每个组要 `fetchAll` 6 个集合（仍是 100 条/页）+ 上传 + 清理。
- 影响：是否超时取决于组织数和数据量；一旦超时，排在后面的组织完全不备份，悬挂租约保留 120 秒阻塞这些组正常写入。这是整份报告里最可信的运维风险——"数据没备上"。
- 修复：按组拆分调用，让每组有独立 20 秒预算；或至少加时间预算检查 + 断点续备。

**F-09 `getInitData` 重复实现** — `src/hooks/useHome.ts:82-128` 与 `:130-151`：`initApp()` 与 `loadInitData()` 逻辑几乎一致，建议合并为带参单函数。

## 3. 更省（成本优化）

**S-01 恢复客户端缺停滞检测（降级；非"空转计费"）** — `src/hooks/useDataManage.ts:1054-1062`：`while(true)` 每次调用都在推进恢复计划（`CHUNK_SIZE=15`，`restore.js:4, 130-163`），属于正常长任务分片轮询，费用与真实工作量成正比，**不是空转**。真正缺的是最大轮次与停滞检测：连续 3 次 `processed` 不前进则中止并提示。固定 300ms 间隔只会拖长恢复时间，不建议加。

**S-02 语音超时双计费（成本泄漏，见 B-06）** — 真实成本泄漏点是 B-06 的超时后双次 ASR 调用；B-05 的配额问题降级为 P1（空 OPENID 绕过、并发超额、fail-open 三件事）。

**S-03 单次 freshness 检查重复调用 `getMenuList`** — `src/services/freshness.ts:46-57, 82-95`：菜单时间戳变化且成员被合并/角色变更时，同一动作内调两次 `getMenuList`（两次计费）。可将首次调用延后到 member 解析之后，或让 `getMembers` 一并返回个人菜单统计。

**S-04 `applyFilter` 双 `searchOrders` 调用** — `src/hooks/useStats.ts:269-273, 286-316, 318-351`：明细与汇总各发一次云函数。建议单次返回 `{list, total, totals, byMonth, aggregate}`。

**S-05 同一请求内重复查询** — `lunch_order/index.js:197` 已查一次 member，各 handler 又重复调用 15 处；`submitOrder` 单次下单查 groups 2~3 次、menu/member 各 2 次；`_touchTimestamps`（`:414-427`）每次写操作多一次 get。建议 dispatch 向下传递 caller、合并查询。

**S-06 首屏全量拉取且未用增量** — `lunch_order/index.js:235-253`：一次拉当日全部订单 + 全量菜单 + 全量成员 + 聚合 + 组文档；`menuTimestamp/membersTimestamp` 已存在却未用于增量。

**S-07 云存储 / 数据库残留无回收** — 恢复计划文件 `planFileID` 成功后从不删除（`restore.js:116-120`）；安全快照 `safety` 不在轮换范围（`lunch_backup/index.js:129-132`）；每次恢复生成永久全量快照（`restore.js:111`）；`order_keys` 锁文档取消后不清理（`lunch_order/index.js:550-563`）；`lunch_voice_usage` 无 TTL；`clearAllData` 不清 `lunch_backups` 文档与云存储文件（`lunch_backup/index.js:305-326`）；CSV/XLSX 导入文件残留。

## 6. 系统性重构建议（更快 / 更省 / 更正确）

**结论：不需要全面重写。** 项目技术债文档已明确"暂不启动全面重构、不为减行数拆文件"，这个判断是对的——`lunch_order/index.js`（约 1813 行）和 `useDataManage.ts`（约 1532 行）的问题不在体积，而在几个反复出现的**结构性缺陷**。以下 4 处是"局部架构级"候选，但按复核结论：**R-1/R-3/R-4 均需先量数据（单日订单峰值、菜单条数、组织数、订单总量）再评估，属于排期项，不进入本周执行清单**；当前只落实 R-2。

### R-1 统一数据访问层 — 更快 + 更省 + 更正确（排期，先量数据再评估）
- 现状：3 份 `fetchAll` 都用 `skip` 深分页；多处裸 `.get()` 无 limit 导致静默截断（`lunch_order/index.js:824, 1273`，见 B-01、M8）；upsert 先 `get` 再 `inc/set` 非原子（`:461-474`，B-12）；rewrite 导入"先删后写"非事务（`lunch_menu/index.js:987-1018`，B-13）。
- 做法：在每个云函数**内部**加一个本地 `dbAccess.js`（不跨函数共享，符合独立部署约束），提供强制 limit 的 `queryAll()`、条件更新/事务版 `upsertAtomic()`、暂存后原子切换的 `replaceInTransaction()`。
- 收益：一次性消灭"静默少单、并发丢计数、导入失败丢数据"三类事故，同时减少全表扫描的耗时与计费。
- 前置：先补对应回归测试再改。

### R-2 时区统一 — 更正确（风险最低，本周唯一落实的重构项）
- 现状：`src/utils/date.ts:1-4` 用设备本地时区，下单 `useOrder.ts:179` 用北京时间，导出文件名又用 UTC（`lunch_order/index.js:1110`）。
- 做法：前后端各一个时间工具函数，所有"今日"和文件名一律走北京时间。
- 收益：消除整类跨时区错乱（B-03），改动面小、易验证。

### R-3 前端请求编排层 — 更快 + 更省（排期，先量数据再评估）
- 现状：`cloudAction`（`baseRepository.ts`）只封装错误，无在途请求去重；一次 freshness 检查调两次 `getMenuList`（S-03）；统计明细与汇总各一次 `searchOrders`（S-04）；管理页进一次 4-5 个云函数；`getInitData` 有两份重复实现。
- 做法：在 `cloudAction` 加"同 action + 同参数"在途 Promise 复用；把管理页初始化、统计筛选各合并为一次服务端聚合调用。
- 收益：直接减少云函数计费次数和首屏延迟；前端可独立灰度，风险低-中。

### R-4 读写边界与租约统一 — 更正确（最后做，行为有变更，先量数据再评估）
- 现状：`getRecentOrders` 属 READ_ACTIONS 却调用 `_autoCancelExpiredPending()` 批量写库（B-10）；`getMonthlyStats` 在读路径上无租约做全量重建（B-09）；恢复备份要求 `activeRequests` 为空，但读请求会写库。
- 做法：把会写库的逻辑移出读路径，改为定时触发或独立 action；让"写操作必经租约 + 时间戳推进"成为统一入口约定，而非每个 handler 自己记得。
- 风险：中高，会改变接口行为；与技术债文档 6.2"出现慢请求再做"的判断一致，建议放到最后并配完整回归。

### 明确不建议做（与既有决策一致）
- **全面重写 `lunch_order` / `useDataManage`**：只在"能独立测试、经常独立修改"的前提下拆导入解析、统计模块，且先补测试。
- **云函数 Layer 统一 `requestGate` 等副本**：微信 Layer 仍在公测，现有 `security.test.cjs` 已硬校验副本一致性，收益不抵风险。
- **统一权限中间件**：容易改变现有权限边界（技术债 2.1 第 4 项已标高风险）。
- **持久化限流、金额改整数分**：无真实滥用、两位小数已够用，属于过度设计。

**建议顺序：本周只做 R-2；R-1 / R-3 / R-4 先量四个数（单日订单峰值、菜单条数、组织数、订单总量）再决定是否排期。** 原"R-2 → R-1 → R-3 → R-4"过于激进，与"当前数据量下收益无法证明"的复核结论冲突，已收窄。
