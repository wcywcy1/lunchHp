# 云数据库外部刷新感知与恢复方案

> 版本：2026-11-23 按当前 HEAD 代码核对。本文描述 `lunch_groups` 时间戳、前端新鲜度检查、watch、月度统计重建与恢复后的失效策略。

## 问题背景

微信小程序云开发中，数据可能通过"清库重写"导入被整体替换。此时前端缓存的时间戳与数据库实际状态脱节，导致：

- 统计页显示旧聚合数据
- 首页不刷新订单列表
- 成员/菜单列表过时

核心矛盾：**前端靠时间戳判断数据新鲜度，但外部操作不会触发云函数里的时间戳更新。**

## 解决思路

在 `lunch_groups`（每个群组只有一条文档）中集中管理所有业务数据的时间戳。任何可能导致数据变化的操作，都必须更新对应时间戳。对于恢复备份这类无法逐月精确判断影响范围的操作，将聚合时间戳清零，触发下次访问时全量重建；普通订单写操作按涉及月份精确重建。

## 时间戳设计

### 时区约定（容易踩坑）

- 云函数统一用北京时间计算“今天”：`new Date(Date.now() + 8h)` 后取 UTC 日期，避免云函数运行环境时区差异。
- 前端 `utils/date.ts` 的 `getTodayString()` 用设备本地时间；国内用户与北京时间一致。若未来面向其他时区，需要把前后端“今天”的判定统一到北京时间，否则跨零点会出现订单日期不一致。
- `cutoffNotice.ts` 也按固定 +8 时区计算截止时间与次日 0 点。

### 存储位置

集合：`lunch_groups`，文档 `_id = groupId`（如 `lunch_hp`）

### 四个业务时间戳 + 两个配置字段

| 字段 | 作用 | 正常更新 | 清零触发 |
|------|------|---------|---------|
| `ordersTimestamp` | 今日订单数据新鲜度 | 每次订单写操作 | 不清零 |
| `dataTimestamp` | 月度统计是否需要重建 | 单条操作或无影响月份时可不动 | 恢复备份完成、清空数据时置 0 |
| `menuTimestamp` | 菜单数据新鲜度 | 每次菜单写操作 | 不清零 |
| `membersTimestamp` | 成员数据新鲜度 | 每次成员写操作 | 不清零 |
| `orderCutoff` | 每天停止接单时间（默认 `10:00`） | `setOrderCutoff` | 不清零 |
| `cutoffDisabled` | 是否禁用停止接单 | `setCutoffDisabled` / `setOrderCutoff` | 不清零 |

> 组文档没有 `notice` / `noticeUpdatedAt`。首页“到点停止接单”的提示由前端根据 `orderCutoff + cutoffDisabled` 本地计算，不写数据库，也没有通知 watch。

### 为什么恢复备份时 `dataTimestamp` 要清零？

恢复完成后订单被整体替换，影响的月份无法在恢复事务里逐月重建。把 `dataTimestamp` 置 0 后，下次访问统计页时 `getMonthlyStats` 检测到 `serverTs === 0`，自动全量 rebuild。

> 订单导入**不是**清零：`importFromCsv/importFromXlsx` 会直接重建本次涉及的月份，并把 `dataTimestamp` 更新为当前时间。

## 前端检测机制

| 页面 | 检测的时间戳 | 检测时机 | 变了之后做什么 |
|------|-------------|---------|------------|
| 首页 useHome | `ordersTimestamp` | onShow（10 秒节流；`checkDataFreshness` → `lunch_menu.getDataTimestamps`，5 秒组织缓存） | 重拉 `getRecentOrders` + `getMonthSummary` |
| 首页 useHome | `menuTimestamp` | 同上 | `freshness.ts` 内部重拉 `getMenuList` |
| 首页 useHome | `membersTimestamp` | 同上 | `freshness.ts` 内部重拉 `getMembers`，并检测当前用户 role 变化，同步 store/session |
| 首页 useHome | `orderCutoff` / `cutoffDisabled` | 同上 + `getInitData` | 更新 `store.groupCutoff/cutoffDisabled`，本地计算截止提示 |
| 管理页 useDataManage | `ordersTimestamp` | onShow（30 秒节流，并行 `getRecentOrders` + `getDataTimestamps`） | 更新今日待确认/已确认与截单配置；watch 变化只重拉订单 |
| 统计页 useStats | `dataTimestamp` | onShow（距上次 >30 秒才加载） | `=0` → 全量 rebuild；否则按缓存/`since` 增量 |
| 菜单页 useMenu | `menuTimestamp` / `membersTimestamp` | onShow | `checkDataFreshness()` 内部重拉对应数据 |

> 关键：所有读操作（getDataTimestamps / getRecentOrders / getRecentMenu / getRecentMembers / getMonthlyStats / getInitData）对所有成员开放，不做权限过滤。普通用户也能在 onShow 时通过时间戳变化感知到自己身份的变更（如 member → admin）。
> `lunch_order.getAllTimestamps` 仍存在，但当前前端没有调用，仅作保留接口。

## 主动切换组织时的缓存与时间戳处理

真实调用链（`pages/group-select/index.vue`）：

```
clearFreshnessCache()            // 丢弃时间戳请求复用
clearAllCache()                  // 清所有缓存 + session；_cacheGeneration++
resetStore()
setActiveGroupId(target)         // 先写 lunch_active_group_id / store.groupId
startInit() → initGroup          // 只校验组织存在
joinGroup                        // 创建/取回目标组织 member
setStore(member/role) + saveSession
switchTab 首页 → watchTodayOrders + checkDataFreshness(getDataTimestamps)
```

要点：

- **不调用 `getInitData`**；主动切换是 `initGroup → joinGroup → 首页 freshness`。
- 旧本地时间戳随 `clearAllCache()` 一起删除；新组织首次 freshness 会全量拉取菜单/成员/今日订单并写入新时间戳。
- 旧组织已排队的延迟缓存写入由 `_cacheGeneration` + `groupId` 双校验丢弃，避免回写新组织缓存。
- 旧 watch 由首页 `onHide → closeAll()` 关闭；group-select 流程本身不持有 watch。
- `lunch_orders` 的 watch 条件使用 `store.groupId`，切换后重建时自动指向新组织。

## 实时数据推送（Watch）

### 方案

使用微信云开发 `Collection.watch` API，在页面打开时建立实时监听，数据变更时推送到客户端，页面隐藏时关闭连接。

### 监听设计

| 页面 | 监听目标 | where 条件 | 变更回调 |
|------|---------|-----------|---------|
| 首页 useHome | `lunch_orders` | `{ groupId, date: today }` | 本地增量 patch `store.recentOrders`，再调用 `getMonthSummary` 刷新月汇总 |
| 管理页 useDataManage | `lunch_orders` | `{ groupId, date: today }` | 不做本地 patch；400ms 防抖后 `loadOrdersOnly()`（1 次 `getRecentOrders`） |

> 当前**没有** `watchGroupNotice`，也不监听 `lunch_groups`；通知能力已替换为“停止接单时间”的本地提示。

### 生命周期管理

```
onShow → 开启 watchTodayOrders
onHide → closeAll() 关闭所有 watch 连接
```

- watch 只在页面可见时存在，切后台自动断开
- 每次 onShow 重新建立连接，watch init 数据被忽略（已有本地数据）
- 指数退避重连：30s → 1min → 2min → 最大 5min；首页 `onError` 还会兜底 `fetchRecentOrders`

### 停止接单提示（替代旧“组通知”）

`lunch_groups` 中使用两个字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `orderCutoff` | string | 每天停止接单时间，默认 `"10:00"` |
| `cutoffDisabled` | boolean | 禁用后到点不截止、不显示提示 |

**设置**：管理员在管理页修改时间 → `lunch_menu.setOrderCutoff`；启用/禁用 → `lunch_menu.setCutoffDisabled`。

**展示**：首页 `useHome` 监听 `store.groupCutoff/cutoffDisabled`，用 `getCutoffNoticeState()` 计算当前是否已过截止时间；截止后到次日 00:00 显示“每天HH:MM停止接单，有需要请电话联系”。不写通知字段、不推送、不调用云函数。

### 资源消耗

#### Watch 连接

| 场景 | 连接数 | 说明 |
|------|--------|------|
| 首页打开 | 1 | watchTodayOrders |
| 管理页打开 | 1 | watchTodayOrders |
| 页面隐藏 | 0 | onHide 自动关闭 |

- watch 走独立长连接通道，不计入数据库读操作数
- 每个用户同时最多约 1-2 个连接，仅在页面打开时存在

#### 数据库/云函数操作

| 操作 | 触发时机 | 云函数调用 | 说明 |
|------|---------|-----------|------|
| watch init | onShow 开启 | 0 | init 快照被忽略 |
| 首页 watch 变更 | 订单变化 | 1 次 `getMonthSummary` | `recentOrders` 为本地 patch，不重拉订单 |
| 管理页 watch 变更 | 订单变化（防抖后） | 1 次 `getRecentOrders` | 不做本地 patch |
| getDataTimestamps | onShow 超过 10s / 30s | 1 次（首页/管理页共用 freshness 的 5s 组织缓存） | 一次性读取时间戳 + 截单配置，兜底 watch 断连 |

### 免费额度覆盖

微信云开发免费额度：数据库每天 10 万次读写。以 20 人团队估算，主要消耗是 onShow 的时间戳检查和订单重拉，远低于免费额度。具体调用次数受页面切换频率、watch 断连和操作量影响，不以固定数字作为验收标准；需要时以云函数日志实测为准。

## 关键实现细节

### 1. 时间戳存在独立集合，不随数据删除而丢失

```
❌ 错误做法：查 lunch_orders 最新一条的 createdAt
   → 记录被删后，时间戳也丢了，无法感知

✅ 正确做法：时间戳存在 lunch_groups 中
   → 数据怎么删都不影响时间戳
```

### 2. 清零时间戳是延迟重建，不是跳过重建

`dataTimestamp = 0` 并不直接重建数据，而是标记"需要重建"。下次用户访问统计页时，`getMonthlyStats` 检测到 `serverTs === 0`，才触发 `doRebuildMonthStats(null)`：

1. `_touchTimestamps({ dataTimestamp: true })` 先占位（防并发）
2. `where({ groupId }).remove()` 清掉旧 `lunch_monthly_stats`（兼容旧格式 _id）
3. 遍历所有 confirmed 订单，按月聚合
4. 逐月 `doc({groupId}_{year}_{month}).set()` 写入（确定性 _id，并发不重复）
5. 返回完整数据 + 新时间戳；失败时把 `dataTimestamp` 重新置 0

优势：**懒执行**——如果没人访问统计页，全量 rebuild 就不会发生。当前只有“恢复备份完成”和“清空数据”会把 `dataTimestamp` 置 0。

### 3. 单条/批量操作精确 rebuild

```
单条 cancelOrder/updateOrder(改价)：已知 order.date → 只 rebuild 那一个月
batchConfirm/batchCancelOrders：按订单 date 去重 → 每个涉及月份 rebuild 一次
导入订单：按导入记录的 date 去重 → 每个涉及月份 rebuild 一次
```

当前代码**没有**“批量操作清零 dataTimestamp、下次访问全量 rebuild”的路径；订单导入直接重建受影响月份。

### 4. 防并发 rebuild

1. **占位**：`getMonthlyStats` 检测到 `serverTs === 0` 时，先 `_touchTimestamps({dataTimestamp:true})`，第二个并发请求读到非零时间戳，不会再次触发全量 rebuild。
2. **确定性 _id**：`doRebuildMonthStats` 用固定 `_id` + `set()` 写入，同一个月永远覆盖同一个文档。
3. **失败回滚**：全量 rebuild 失败时重新置 `dataTimestamp=0`，下次访问可重试。
4. **删除标记**：某月最后一条 confirmed 订单消失时写入 `deleted:true`，增量客户端据此移除缓存月份。

### 5. 订单导入的实际时间戳行为

前端订单导入是**一次云函数调用**（`importFromCsv` 或 `importFromXlsx`），不是分批循环；`_importOrdersFromRows` 的 `isLastBatch` 默认 `true`：

| 步骤 | mode | 时间戳 |
|------|------|------|
| 订单导入（CSV/XLSX） | `rewrite` 或 `append` | 重建受影响月份；更新 orders/data/menu/members 时间戳 |
| 菜单/成员 CSV 前端分批 | 第 1 批 `rewrite`，后续 `rewrite_continue` | 只更新 menu/members 时间戳，不处理月度统计 |

`rewrite_continue` 在云函数中没有专门分支：只因 `mode !== 'rewrite'` 而不清空、`mode !== 'append'` 而不去重。

### 6. 前端 loadStats 刷新策略

| 场景 | forceRefresh | 传 since? | 行为 |
|------|:-:|:-:|------|
| onMounted | false | 可能 | 30 分钟内用前端缓存，否则请求云端 |
| onShow（距上次 >30s） | false | 可能 | 请求云端；有 `MONTHLY_STATS_TIME` 且在 1 小时内则带 `since` |
| 下拉刷新 | true | **否** | 全量请求云端 |

收到云端响应的处理：
- `incremental=true && data.length>0` → 增量合并缓存
- `incremental=false` → 直接用新数据
- `incremental=true && data.length===0` → **保持现有数据不变**（语义是"无增量变更"，不是"无数据"）
- 增量中 `deleted:true` → 从缓存移除该月

## 云函数与数据库调用次数（量级参考）

> 下面只列关键路径的调用构成，不再给出精确到个位的 DB 读写数。实际次数受文档数量、分页、重试和并发影响，验收时应以云函数日志为准。

### 订单导入（M 条订单，K 个月份）

| 步骤 | 云函数调用 | DB 读 | DB 写 |
|------|:-:|:-:|:-:|
| 前端上传文件 | 0（直传云存储） | — | — |
| `importFromCsv` / `importFromXlsx` | 1 | 成员 + 菜单全量；`append` 时再按文件日期查订单 | `rewrite` 清空订单；ceil(M/100) 插入；缺失成员/菜品批量插入；K 次月度重建；时间戳更新 |
| 统计页下次访问 | 1 | 月度统计 + groups | 通常 0（已重建） |

### 统计页触发全量 rebuild（K 个月份，M 条订单）

| 步骤 | 云函数调用 | DB 读 | DB 写 |
|------|:-:|:-:|:-:|
| `getMonthlyStats` | 1 | groups + monthly_stats | 占位 dataTimestamp |
| `doRebuildMonthStats(null)` | — | ceil(M/1000) 分页读订单 | 1 次清空旧 stats + K 次 set |
| 返回前再读 | — | monthly_stats + groups | — |

### 统计页普通访问

| 场景 | 云函数调用 | 说明 |
|------|:-:|------|
| 全量请求（无 since） | 1 | 读 groups + monthly_stats |
| 增量请求（有 since） | 1 | 读 `updatedAt > since` 的月度统计 |
| 增量返回空 | 1 | 可能额外 count；总数为 0 时触发一次全量重建 |

### 单条订单操作

| 操作 | 云函数调用 | 主要写入 |
|------|:-:|------|
| submitOrder | 1 | 订单事务 + 下单锁 + 菜单计数 + 成员时间 + 个人统计 + 四个时间戳 |
| cancelOrder / batchConfirm / batchCancelOrders | 1 | 订单状态 + 涉及月份 rebuild + orders/data 时间戳 |
| updateOrder（改价） | 1 | 订单 + 该月 rebuild + orders/data 时间戳 |
| updateOrder（改备注） | 1 | 订单 + ordersTimestamp |
| cancelMyOrder / requestCancelOrder / rejectCancelRequest | 1 | 订单字段 + ordersTimestamp |

### 单月 rebuild

| 步骤 | DB 读 | DB 写 |
|------|:-:|:-:|
| 删除该月旧 stats | — | 1 |
| 分页读取该月 confirmed 订单 | ceil(该月订单数/1000) | — |
| set 该月 stats（或 deleted 标记） | — | 1 |

## 迁移检查清单

当新增一个可能修改数据库的操作时，确认以下事项：

- [ ] 该操作影响了哪个集合？（orders / members / menu / monthly_stats / groups / user_menu_stats / order_keys / audit_logs）
- [ ] 对应的时间戳是否已更新？（ordersTimestamp / membersTimestamp / menuTimestamp / dataTimestamp）
- [ ] 是否影响了月度统计？如果是 → 单条/批量操作按涉及月份 rebuild；只有恢复备份、清空数据这类无法逐月判断的场景才把 `dataTimestamp` 置 0
