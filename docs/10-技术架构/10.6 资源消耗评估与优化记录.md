## 二、单次操作资源消耗（优化后）

## 三、删除菜单/人员对历史订单的影响

**结论：不影响。** 代码证据：

- order 同时存 `memberId`/`menuId`（引用）**和** `memberName`/`menuName`（名称快照）
- deleteMember / deleteMenuItem 只删自身记录，无级联
- 历史订单导出、显示、月度统计重建都依赖快照字段，不受影响
- 唯一副作用：`menuId`/`memberId` 变悬空引用，`lunch_user_menu_stats` 留孤儿数据（不影响功能）

## 四、典型案例资源消耗

### 场景描述

- **10 个成员**，每人：登入 → 切到菜单页使用 5 分钟 → 给自己点 1 单 → 给别人点 1 单 → 切到首页确认 → 离开；中间再登入首页 2 次
- **管理员 1 人**：每天停留在管理页约 2 小时；每天退出/登入/切页各约 20 次

### 单个成员消耗明细

| 维度 | 数值 |
|---|---|

| DB 读 | 10×9 + 133 = **~223 次/天** |
| DB 写 | 10×10 + 7 = **~107 次/天** |
| realtime watcher | 管理员管理页 + 首页常驻；各成员在线时各 2 个（todayOrders + groupNotice） |
| 内存峰值 | 单用户 ~500KB，云函数实例 ~100MB |

### 月度估算（30 天）

| 维度 | 数值 |
|---|---|
| 云函数调用 | ~6,120 次/月 |
| DB 读 | ~6,690 次/月 |
| DB 写 | ~3,210 次/月 |

> 注：以上为优化后数值。关键优化带来的节省：
> - **getAllTimestamps 合并**：首页 onShow 从 2-3 次云函数（fetchNotice + checkFreshness + getDataTimestamps）降至 1 次，DB 读从 2-3 次降至 1 次
> - **watch 变更本地 patch**：订单变更时从 1 次 getRecentOrders（100+ DB 读）降至 0 次额外 DB 读
> - **watch 通知推送**：管理员通知无需成员轮询检测，在线成员 0 云函数 0 DB 读即可收到
> - **时间戳对比替代固定节流**：未变化时 0 额外拉取，有变化才按需拉取，比固定 10s/30s 节流更精准
> - 优化前（批量取消未改、无 watch、aggregate 全量扫描、多云函数独立取时间戳），同等场景云函数调用约 +50%、DB 读约 +70%
> - 微信云开发免费额度：云函数每天 50 万次调用、数据库每天 10 万次读写，当前消耗远低于免费额度（< 1%）

## 五、realtime 策略

- **管理员**：home 页和 data 页均有 today orders watcher + group notice watcher，实时看到新订单和收到通知（硬约束，已保证）
- **成员**：home 页有 today orders watcher（可实时看到他人的订单变更，本地 patch 更新，0 额外 DB 读）+ group notice watcher（实时接收管理员通知）；秒级延迟可接受
- **用户身份变更**：管理员通过 setAdmin 将 member→admin 时，更新 membersTimestamp；被变更用户下一次切到首页时，getAllTimestamps 检测到 membersTimestamp 变化 → 重拉 getRecentMembers → 检测到当前用户 role 已变化 → 自动更新 store.member + store.role + saveSession，无需重新登录
- **watch 与时间戳双保险**：watch 在前台时实时推送；onShow 时通过 getAllTimestamps 兜底（解决 watch 断连期间的漏单）
- watcher 独立于 HTTP 节流，不影响数据实时性；同时 O8 提供指数退避重连，watch 断连不会遗漏数据（由 onShow getAllTimestamps 兜底）

## 六、剩余风险点

1. **getRecentOrders 单次 get 上限 1000 条**：订单 > 1000 时需分页，当前 4000 条规模下 home 页只取最近 30 天（< 1000），够用；可通过 limit+skip 分页优化
2. **doRebuildMonthStats 全量聚合**：订单量大时（>10000）rebuild 耗时，可改增量更新（每次 submitOrder/confirmOrder 时按月统计 patch）
3. **TCB 批量 add 返回 _ids**：依赖 TCB 返回 `_ids` 数组，环境差异需回退单条 add；当前生产环境已验证正常
4. **watch 连接上限**：TCB 每个集合的 watch 连接数有上限（默认较高），10 人团队 20-30 个并发连接无压力；如扩展到 100+ 成员需评估 watch 策略，可考虑只在管理员页启用 watch，成员页依赖 onShow 时间戳
5. **虚拟成员关联场景**：adminLinkVirtualMember 涉及多步骤 DB 操作，当前无事务包装；极端情况下中途失败可能留下部分合并数据；实际场景中操作频率低，可手动重试
6. **云存储头像文件清理**：用户多次修改头像会产生旧文件，当前无自动清理机制；可定期在 backup 云函数中扫描未引用的 avatar 文件
