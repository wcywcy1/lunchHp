## 二、当前调用链与调用次数（量级参考）

### 启动场景（当前调用链）

| 场景 | 云函数调用 | 说明 |
|------|:-:|------|
| 冷启动，有 session，时间戳未变 | 1 | `checkDataFreshness` → `lunch_menu.getDataTimestamps`；5 秒内复用，通常不再拉数据 |
| 冷启动，有 session，订单时间戳变化 | 2 | 时间戳 + `getRecentOrders`；随后可能再 1 次 `getMonthSummary` |
| 冷启动，有 session，菜单/成员时间戳变化 | 1-3 | 时间戳 + `getMenuList` / `getMembers`（freshness 内部并行） |

## 三、删除菜单/人员对历史订单的影响

**结论：不影响。** 代码证据：

- order 同时存 `memberId`/`menuId`（引用）**和** `memberName`/`menuName`（名称快照）
- deleteMember / deleteMenuItem 只删自身记录，无级联
- 历史订单导出、显示、月度统计重建都依赖快照字段，不受影响
- 唯一副作用：`menuId`/`memberId` 变悬空引用，`lunch_user_menu_stats` 留孤儿数据（不影响功能）

## 四、历史估算（已删除）

原“典型案例/每日/月度调用量/免费额度占比”等数字基于旧调用链（getAllTimestamps、groupNotice、旧 watch 方案），**不是当前 HEAD 的实测结果**，已删除，避免被误读为当前性能事实。

当前性能与资源消耗需以实际云函数日志、数据库监控和运行数据测量为准；本文件不提供推算的精确数字。

## 五、当前 realtime 策略

- **管理员**：首页和管理页均有 `watchTodayOrders`，可实时看到今日订单变化；首页本地 patch，管理页 400ms 防抖后重拉订单
- **成员**：首页有 `watchTodayOrders`，看到他人订单变更；本地 patch + 1 次月汇总刷新
- **用户身份变更**：创建者通过 setAdmin 将 member→admin 时更新 membersTimestamp；被变更用户下一次 onShow 的 freshness 检查检测到变化 → 重拉成员 → role 变化 → 自动更新 store.member/role/session，无需重新登录
- **watch 与时间戳双保险**：watch 在前台时实时推送；onShow 时通过时间戳兜底（解决 watch 断连期间的漏单）
- **没有 groupNotice watch**；停止接单提示完全由前端按配置本地计算
- watcher 独立于 HTTP 节流，不影响数据实时性；断连按指数退避重连

## 六、当前剩余风险点

1. **菜单/成员列表分页（已修复 2026-11-23）**：`getInitData`、`getMenuList`、`getMembers`、`getRecentMenu`、`getRecentMembers` 原使用 `.get()` 未设置 limit，受云端默认 100 条约束（详见 10.3）。现已统一改为 `fetchAll` + 内存排序（菜单按 `sortNo`、成员按 `joinedAt`），`business-logic.test.cjs` 覆盖 120 条菜单/成员场景。其余列表接口（`getPendingCancelRequests`、`getConfirmedBySupplier`、`downloadConfirmed` 等）仍使用 `.get()`，当前数据量远低于 100 且后两者前端未调用；数据量增长时按同样方式处理。
2. **doRebuildMonthStats 全量聚合**：订单量大时（>10000）rebuild 耗时；当前每次导入会重建受影响月份，未做增量聚合。
3. **TCB 批量 add 返回 _ids**：依赖 TCB 返回 `_ids` 数组，环境差异需回退单条 add；当前生产环境已验证正常。
4. **watch 连接上限**：TCB 每个集合的 watch 连接数有上限，10 人团队 20-30 个并发连接无压力；扩展到 100+ 成员需评估是否只在管理员页启用 watch。
5. **虚拟成员关联无事务**：`adminLinkVirtualMember` 涉及多步骤 DB 操作，极端情况下中途失败可能留下部分合并数据；操作频率低，可手动重试。
6. **云存储文件清理**：备份文件有轮换上限，删除组织时会清理该组织的备份文件与无其他组织引用的头像；文件删除失败会记录该批 fileID 与错误信息，便于事后手工清理。但用户多次修改头像产生的旧文件、`lunch/exports`、`lunch/imports`、`lunch/restore` 下的残留文件没有自动清理机制（云存储无目录列举 API，只能删除数据库中有 fileID 记录的文件）。恢复计划文件在恢复成功后仍保留。
7. **reportError 未实现**：前端错误仅 `console.error`，没有服务端聚合。

## 七、当前状态校准（2026-11-23）

| 主题 | 当前实现 |
|------|---------|
| 时间戳检查 | 前端 `checkDataFreshness` → `lunch_menu.getDataTimestamps`；首页 10 秒节流，管理页 30 秒节流；`lunch_order.getAllTimestamps` 未被前端调用 |
| 订单范围 | `getRecentOrders` / `getInitData` 只取**当天**订单，不是最近 30 天；`getRecentMenu` 返回全部菜单 |
| watch | 只有 `watchTodayOrders`；首页 patch + 月汇总刷新；管理页防抖重拉；无 groupNotice |
| 通知 | 无组通知；停止接单提示由 `orderCutoff`/`cutoffDisabled` 本地计算 |
| 导入 | 订单导入单次云函数调用，直接重建受影响月份并更新四个时间戳；菜单/成员 CSV 才由前端分批 |
| 统计重建 | `dataTimestamp=0` 用于恢复备份和清空数据后；普通订单操作按月份精确 rebuild；空月份写 `deleted:true` 标记 |
| 月度统计导出 | `downloadMonthlyData` 按 `year` / `months` 过滤，并排除 `deleted` 月份；云函数失败时前端用筛选后数据兜底 |
| 缓存写入 | `setCache` 300ms 合并 + `_cacheGeneration` + `groupId` 双重校验；会话 TTL 7 天 |
| 多组织 | 无 `APP_MODE`；选组页创建/加入/切换，`lunch_hp` 仅默认回退；`initGroup` 不自动建组 |
| 删除组织 | 头像引用查询在任何删除前完成，失败即终止且不改数据；级联删除业务数据、备份记录/文件、下单锁；头像文件仅在其他组织无引用时删除；文件删除失败记录 fileID 但不阻断删除；导出/导入/恢复残留文件无法按组织列举，暂不清理 |
| 安全/恢复 | `requestGate` 写请求租约 120 秒 + 恢复维护锁；恢复协议 v2 分片 15 条/事务；备份内容存云存储并带 sha256 |
