## 七、大数据量与成本优化策略

### 7.1 关键洞察

99% 的使用场景是当天点餐。核心结论：日常操作主要看当天数据，加载最近订单；历史数据在统计页按需加载。

### 7.2 三层加载架构

```
┌─────────────────────────────────────────────────┐
│  第一层：基础数据（首次进入组织时加载）              │
│  - 今日订单 fetchAll({ date: today })              │
│  - 菜单列表、成员列表                              │
│  - 当月汇总、时间戳、截单配置                       │
│  → 1次云函数 getInitData                           │
├─────────────────────────────────────────────────┤
│  第二层：月度统计（统计页按需加载）                 │
│  - monthly_stats 全量/增量刷新                    │
│  → getMonthlyStats                               │
├─────────────────────────────────────────────────┤
│  第三层：历史详单（筛选/导出时按需加载）            │
│  - 按筛选条件从云端查询                            │
│  → searchOrders / exportOrders / getHistoryOrders │
└─────────────────────────────────────────────────┘
```

**`getInitData` 内部执行（当前代码）：**
1. `ensureCollections()` + `_autoCancelExpiredPending()`（按组织 60 秒实例节流）
2. 内联加入组织：按 openid 查成员；不存在则创建（创建者自动为 creator），不单独调用 `lunch_menu.joinGroup`
3. 当月聚合（aggregate，排除 `cancelled`）→ `totalAmount` + `count`
4. 今日订单：`fetchAll({ groupId, date: today })`，按 `createdAt` 倒序；不是“最近 30 天”
5. 菜单全量（`sortNo` 升序）+ 大众统计默认值 + 当前用户个人点餐统计
6. 成员全量（`joinedAt` 升序）
7. 返回 `member/role/isNew`、时间戳、`orderCutoff`、`cutoffDisabled`
8. 不返回 `notice`；组文档没有通知字段

> 调用时机：`getInitData` 只在首页 store 无 member（异常会话/首次数据缺失）和恢复备份后由 `initApp` 调用；正常的组织创建/加入/切换由 `group-select` 的 `initGroup → joinGroup` 完成，主流程不依赖 `getInitData`。
>
> 注意：`getInitData` 查询“今日订单”而非固定的最近 N 条，避免导入历史订单把当天数据挤出窗口。菜单/成员使用 `fetchAll` 完整分页（单页 1000 条）后按 `sortNo` / `joinedAt` 排序，不再受云端默认 100 条限制（见 10.3、10.6）。

### 7.3 数据刷新保障

| 机制 | 触发方式 | 说明 |
|------|---------|------|
| **自动刷新** | 首页 onShow（10 秒节流） | 调 `checkDataFreshness()` → `lunch_menu.getDataTimestamps`（按组织 5 秒缓存 + 并发复用）；只有 `ordersTimestamp` 变化时首页重拉 `getRecentOrders`；菜单/成员变化在 freshness 内直接重拉 |
| **下拉刷新** | 用户手动下拉 | 强制调用 `getRecentOrders`，同时刷新月汇总 |
| **写后即时** | 本人下单/取消/申请取消 | 前端更新本地状态；取消/申请取消主动 `fetchRecentOrders`；下次 onShow 再走 freshness |
| **管理页刷新** | onShow（30 秒节流）或操作后 | 并行 `getRecentOrders` + `getDataTimestamps`；确认/取消/导入等操作后主动 `loadData` |
| **他人变化** | 其他客户端订单变化 | 不做实时推送；在下次 onShow、下拉刷新或管理员操作后的 `loadData` 时可见 |

### 7.4 与账本策略的对比

| 维度 | 账本 | 点餐 |
|------|------|------|
| 默认加载范围 | 全量 records | 最近订单 + 当月聚合 |
| 历史数据 | 渐进式加载+本地缓存 | 按需从云端查询 |
| 实时同步 | `checkDataFreshness`（轮询） | `checkDataFreshness` + 时间戳检查 |
| 统计数据 | local/cloud 双模式 | 统一用 monthly_stats |
| 分片存储 | 需要 | 不需要 |

**关于刷新机制的说明：**

- 客户端不直接访问数据库，也不使用 `Collection.watch`；所有业务数据通过云函数获取。
- `checkDataFreshness` 是页面 onShow 时的时间戳检查：稳定、不依赖长连接；代价是存在节流/页面切换延迟，不是实时推送。
- 当前点餐方案采用“onShow + freshness + 下拉刷新 + 操作后主动刷新”，数据最终一致；不追求跨客户端实时推送。

### 7.5 点餐程序的时间戳检查机制

**与 `checkDataFreshness` 的区别：**

| 维度 | 账本 `checkDataFreshness` | 点餐时间戳检查 |
|------|------------------------|--------------|
| 性质 | 一个综合检查函数，通常检查整个数据集/多个集合 | 分散的多时间戳对比，每种数据独立检查 |
| 检查对象 | 可能是全局时间戳、版本号或 hash | `ordersTimestamp`（订单）、`menuTimestamp`（菜单）、`membersTimestamp`（成员）、`dataTimestamp`（月度统计）；截单配置随 `getDataTimestamps` 一起返回 |
| 触发方式 | 页面 onShow、写操作后等固定时机 | 按数据类型和页面按需触发 |
| 粒度 | 粗粒度，可能一次检查刷新多项 | 细粒度，只刷新发生变化的数据 |

**点餐程序各时间戳的检查时机：**

| 时间戳 | 对应数据 | 检查触发时机 | 处理动作 |
|--------|---------|-------------|---------|
| `ordersTimestamp` | 今日订单 | 首页 `onShow`（10 秒节流）、下拉刷新 | `checkDataFreshness` → `lunch_menu.getDataTimestamps`（5 秒组织缓存）；不一致则调用 `getRecentOrders` 重拉 |
| `menuTimestamp` | 菜单列表 | 首页/菜单页/管理页 `onShow` 的 freshness 检查 | 不一致则 `getMenuList` 重拉并写缓存 |
| `membersTimestamp` | 成员列表 | 同上 | 不一致则 `getMembers` 重拉，并检测当前用户 `role` 变化后同步 store/session |
| `dataTimestamp` | 月度统计 | 统计页 `loadStats` | 为 0 时触发全量重建；非 0 且内存已有统计数据时按 `since` 增量刷新，冷启动先全量 |
| `orderCutoff` / `cutoffDisabled` | 停止接单时间 | 随 `getDataTimestamps` 返回；也随 `getInitData` 返回 | 更新 `store.groupCutoff`，首页本地计算截止提示 |

**关键规则：**
- 写操作（如下单、确认、取消）**不更新自己的本地时间戳**。这样自己下次检查时会因"本地旧时间戳 < 服务端新时间戳"而重新拉取最新数据；其他用户亦然——服务端时间戳已被写操作更新，而他们本地仍保留旧时间戳，下次检查时同样会触发同步
- 客户端刷新完全依赖云函数 + onShow/freshness + 主动刷新，不依赖任何客户端数据库监听
- 不同页面只检查与本页相关的时间戳，避免不必要的云函数调用
- **当前前端实际调用的是 `lunch_menu.getDataTimestamps`**，不是 `lunch_order.getAllTimestamps`。`lunch_order.getAllTimestamps` 仍然存在且列入只读 action，但当前前端未使用，属于保留接口。
- `statsLoadTime`/`recentLoadTime` 放在 store 中，切组时统一重置。

### 7.6 客户端数据访问边界

- 所有 `lunch_*` 集合的小程序端权限为“所有用户不可读写”；客户端不能直接查询或监听数据库。
- 所有业务数据通过云函数读取/写入；云函数使用服务端数据库权限。
- 多组织隔离的安全边界在云函数的 `groupId` 过滤、成员校验和角色校验，而不是客户端查询条件。
- 因此不再使用 `Collection.watch`，也不存在 watch 断连、指数退避重连或 close 生命周期代码。

## 八、缓存与云函数调用策略

### 8.1 核心原则

> TCB 免费额度按每日数据库读写量计算（不是按单条精确计费），仍有限额；云函数调用次数和响应体大小是更直接的瓶颈。优化优先级：
> 1. 尽量少调用云函数
> 2. 数据不经过前端中转
> 3. 写操作不更新自己的本地时间戳，下次检查时能发现服务端已更新
> 4. 自己的写操作不更新自己的本地时间戳 — 你下次检查时会因"本地旧时间戳 < 服务端新时间戳"而重拉；别人也一样，他们本地时间戳仍是旧的，服务端时间戳已被你的写操作更新，下次检查时同样会触发同步。**你永远不能改别人的本地时间戳，只有服务端时间戳是大家共同对比的基准。**
> 5. 外部批量导入/清库重写时，由云函数更新对应时间戳并重建受影响月份；恢复备份完成时把 `dataTimestamp` 置 0，触发下次访问全量重建
> 6. 当天数据优先，历史按需加载

### 8.2 缓存架构

```
Vue 3 Reactive State
    ↓
内存缓存标志 + 时间戳
    ↓
本地持久化存储（uni.getStorageSync / localStorage）
```

### 8.3 新鲜度检查策略

```
首页 onShow：
  1. 有 session 且 member 已加载 → 进入 freshness 检查
  2. 距上次 freshness 检查 < 10 秒 → 跳过
  3. 超过 10 秒 → checkDataFreshness() → lunch_menu.getDataTimestamps
     （按组织 5 秒缓存 + 并发 Promise 复用）
     ├─ ordersTimestamp 不一致 → getRecentOrders 重拉 + refreshMonthSummary
     ├─ menuTimestamp 不一致 → freshness 内部 getMenuList 重拉
     ├─ membersTimestamp 不一致 → freshness 内部 getMembers 重拉并同步本人 role
     └─ 全部一致 → 只更新 recentLoadTime
  4. 下拉刷新 → 强制 getRecentOrders + getMonthSummary

管理页 onShow：
  1. 30 秒内已全量加载 → 跳过加载
  2. 否则并行 loadAdminData(getRecentOrders, getDataTimestamps)
  3. 再加载取消申请 + 菜单列表
  4. "历史"折叠面板展开时 → getHistoryOrderCount / getHistoryOrders
  5. 管理员确认/取消/导入等操作后 → loadData / loadMenuList 主动刷新
```

### 8.4 写操作策略

复用账本核心规则：**写操作不更新自己的本地时间戳**。

```
提交订单流程：
1. 调用云函数 submitOrder → 服务端 ordersTimestamp/menuTimestamp/membersTimestamp/dataTimestamp 更新
2. 本地 state.recentOrders.unshift（即时显示）
3. 用云函数返回的 updatedMenu/updatedMember 替换本地对象，持久化（setCache 300ms 防抖合并）
4. 自己的本地时间戳保持旧值 ← 关键！

下次 onShow（>10 秒）→ checkDataFreshness：
  → 本地旧时间戳 ≠ 服务端新时间戳 → 重新拉今日订单
```

> 为什么不能更新自己的本地时间戳？
> 如果写完后把本地时间戳也改成最新，下次时间戳检查就会发现"本地 == 服务端"，跳过拉取，导致自己看不到服务端的真实最新状态（比如其他人在你写操作之后提交的数据）。保持旧值，才能强制下次检查触发同步。
>
> 其他用户如何看到我的变化？他们本地也保留着自己的旧时间戳，我写操作更新了服务端时间戳，他们下次检查时也会触发同步。

### 8.5 外部导入/清库场景下的时间戳策略

所有外部数据导入（管理页上传 CSV/XLSX）**必须走云函数**，由云函数负责更新时间戳。直接绕过云函数修改数据库，前端无法感知。

| 导入操作 | 数据集合 | 更新的时间戳 | 月度统计处理 | 说明 |
|---------|---------|------------|------------|------|
| `importFromCsv` / `importFromXlsx`（订单） | `lunch_orders` | `ordersTimestamp`、`dataTimestamp`、`menuTimestamp`、`membersTimestamp` | 对本次涉及的月份执行 `doRebuildMonthStats` | `rewrite` 先清空订单；`append` 按 `date+memberId+menuId` 去重；缺失成员/菜品自动创建 |
| `importMembers` 追加 | `lunch_members` | `membersTimestamp` | 不处理 | 只管理未绑定微信的普通成员 |
| `importMembers` 清库重写 | `lunch_members` | `membersTimestamp` | 不处理 | 只删除未绑定、`role=member`、`isVirtual=true` 且不在保留名单中的成员；不会清零 `dataTimestamp` |
| `importMenuItems` 追加/重写 | `lunch_menu` | `menuTimestamp` | 不处理 | 菜单不影响已有订单的 supplier/price |

> 当前订单导入**不会**把 `dataTimestamp` 清零；它在每批导入结束时直接重建受影响月份并把 `dataTimestamp` 更新为当前时间。`dataTimestamp=0` 只用于“恢复备份完成后要求下次访问全量重建”。CSV 订单导入由前端一次性上传文件，云函数默认 `isLastBatch=true`；前端没有向云函数传 `isLastBatch`。

### 8.6 冷启动恢复

```
App onLaunch → restoreSession() → restoreFromCache()：
1. 从 localStorage 读取 members / menu / recentOrders / 时间戳
2. 直接填充 state
3. 用户立即看到上次数据
4. 首次 onShow → 后台静默验证并更新
```

### 8.7 统计页加载策略

```
进入统计页：
  1. onMounted → loadStats(false)
     ├─ 距上次加载 < 30 分钟且有缓存 → 直接使用缓存，不发请求
     └─ 否则请求 getMonthlyStats；内存已有统计数据且 MONTHLY_STATS_TIME 在 1 小时内则带 since 做增量，冷启动先全量
  2. onShow → 距上次 >30 秒才 loadStats(false)
  3. 下拉刷新 → loadStats(true)，强制全量
  4. 筛选变更 → searchOrders(aggregateBy=supplier) 实时聚合 + 分页详单
  5. 下载 → downloadMonthlyData（云存储 CSV，失败时前端本地生成兜底）
```

`getMonthlyStats` 内部逻辑（当前代码）：
- `dataTimestamp === 0` → 先占位更新 + `doRebuildMonthStats(null)` 全量重建 + 返回全量；失败则重新置 0
- 有 `since` 参数 → `updatedAt > since` 的月份作为增量返回；无变更时返回空数组 + `incremental=true`
- 有 `since` 且增量与总数都为空 → 再触发一次全量重建
- 无 `since` → 查询全部；若库中没有任何月度统计，则触发一次全量重建
- 返回的 `deleted:true` 月份由前端 `_mergeStats` 从缓存移除

### 8.8 关于"缓存永久有效"的说明

`cacheConfig.ts` 中时间戳缓存 TTL = 0，**仅表示本地存储的时间戳不会因"过期"被自动丢弃**，不是说数据永远不刷新。

实际是否刷新，取决于**服务端时间戳与本地时间戳是否一致**：

```
本地时间戳 = 服务端时间戳  →  跳过，不刷新
本地时间戳 ≠ 服务端时间戳  →  触发对应数据的重拉/重建
```

因此：
- 外部批量导入/清库重写时，**服务端时间戳必须被更新**，前端才能感知
- 恢复备份完成后把 `dataTimestamp` 置 0，就是让"本地旧值 ≠ 服务端 0"，从而触发统计页全量重建
- 订单导入不走清零，而是直接重建受影响月份并更新时间戳
- 如果绕过云函数直接改数据库，前端的时间戳对比会失效，缓存将长期过期

### 9.2 多组织说明

当前**没有** `APP_MODE`，多组织始终可用：
- `createGroup(groupName)`：组名全局唯一，组ID系统生成 `lunch_{ts}_{random}`
- `listJoinedGroups()`：列出当前用户已加入的所有组
- `joinGroupByName(groupName)`：按组名查找并加入；**开放入组是确认的产品规则**，不设邀请码、审批或申请流程
- `deleteGroup()`：创建者删除组织；清理业务数据、备份记录/文件、下单锁，并仅删除无其他组织引用的头像文件
- `initGroup()`：仅校验组织是否存在，不存在返回 404；不会自动建组
- 新成员按组名加入后更新 `membersTimestamp`，其他端通过 freshness 感知
- 前端通过 `ACTIVE_GROUP_ID_KEY` 保存当前激活组
- 所有 `lunch_*` 集合客户端不可读写；业务数据统一通过云函数访问，多组织隔离的安全边界在云函数的 `groupId`/成员/角色校验

**主动切换组织的真实调用链：**

```
首页 Header → reLaunch 选组页
→ switchToGroup:
   clearFreshnessCache() / clearAllCache()（含 session） / resetStore()
   → setActiveGroupId(target)       // 写 lunch_active_group_id
   → startInit() = initGroup        // 只校验存在；404 清会话回选组页
   → joinGroup                      // 创建/取回目标组织 member
   → setStore(member/role) + saveSession
   → switchTab 首页
→ 首页 onShow: checkDataFreshness(getDataTimestamps)
```

> 主动切换是 `initGroup → joinGroup → freshness`，**不是 `initGroup → getInitData`**。`getInitData` 只在冷启动 store 无 member（内部内联 join）和恢复备份后调用。

### 9.3 月度统计重建（核心防并发设计）

```javascript
// doRebuildMonthStats 关键实现
async function doRebuildMonthStats(targetYearMonth) {
    // 1. 清除旧记录
    await db.collection('lunch_monthly_stats').where(statsWhere).remove()

    // 2. 拉取 confirmed 订单并聚合
    const monthMap = {}
    // ... 聚合计算 ...

    // 3. 用确定性 _id 写入，避免并发重复
    const docId = `${GROUP_ID}_${year}_${month}`
    await db.collection('lunch_monthly_stats').doc(docId).set({ data: { ... } })

```

`getMonthlyStats` 中 `dataTimestamp === 0` 时先 `_touchTimestamps({dataTimestamp:true})` 占位，防止并发请求重复重建；失败时把 `dataTimestamp` 重新置 0。

### 9.4 导入数据（importFromCsv / importFromXlsx）

**入口：**
- `importFromCsv(fileID, mode)`：服务端下载 CSV，自动识别 UTF-8/UTF-16/GBK，解析后导入订单
- `importFromXlsx(fileID, mode, importType)`：服务端解析 Excel 第一个 sheet；`importType` 为 `orders`/`menu`/`members`
- 前端导入前把文件上传到 `lunch/imports/{groupId}/`，`requestGate.validImportFile` 校验归属，避免跨组织导入

**模式：**
- `rewrite`：清空现有数据后导入（订单/菜单/成员各自范围）
- `append`：追加导入；订单按 `date+memberId+menuId` 去重（只查询文件涉及日期），菜单/成员按名称规则处理
- 前端菜单/成员 CSV 分批时会传 `rewrite_continue` 给后续批次；云函数只在 `mode === 'rewrite'` 时清空、只在 `mode === 'append'` 时去重，因此 `rewrite_continue` 的实际语义是“不清理、不去重，继续写入”

**订单自动创建：**
- 缺失成员 → 创建 `isVirtual=true`、`openid=''` 的虚拟成员
- 缺失菜品 → 使用 CSV 数据中的 supplier/price 自动创建

**批量处理：**
- 云函数内部 `BATCH_SIZE=100`
- 导入结束后对受影响月份执行 `doRebuildMonthStats`，并更新 `ordersTimestamp/dataTimestamp/menuTimestamp/membersTimestamp`
- `_importOrdersFromRows` 的 `isLastBatch` 默认 true；当前前端**不传** `isLastBatch`，所以每次 CSV 订单导入都会立即重建
- 返回 `{ count, errors, skipped, skippedDetails }`，不返回完整 results 数组（避免超 1MB）

**导入操作的时间戳更新（与 8.5 节对照）：**

| 导入操作 | 云函数 | 时间戳更新 | 月度统计 |
|---------|--------|-----------|---------|
| `importFromCsv`（订单） | `lunch_order` | `ordersTimestamp` + `dataTimestamp` + `menuTimestamp` + `membersTimestamp` | 重建受影响月份 |
| `importFromXlsx`（订单） | `lunch_order` | 同上 | 重建受影响月份 |
| `importMembers` rewrite/append | `lunch_menu` | 更新 `membersTimestamp` | 不处理 |
| `importMenuItems` rewrite/append | `lunch_menu` | 更新 `menuTimestamp` | 不处理 |

所有导入完成后，服务端时间戳已经改变，前端在下次 `onShow` / `loadStats` 时即可感知并刷新。

### 9.4.1 虚拟成员合账（linkVirtualMember / adminLinkVirtualMember）

**目标**：虚拟成员 A 与微信成员 B 确认为同一人后，保留 A 的 `_id` 和预置姓名，把 B 的 openid 绑定到 A，双方订单和个人统计统一归属 A。

**服务端流程：**

1. **认领事务（2 个成员文档 + 组织时间戳）**：校验 A 未被认领、B 同组且 openid 匹配；更新 A 的 `openid`、`mergeFromMemberId=B._id`、role/昵称/头像/隐私；删除 B；更新 `membersTimestamp`。认领后同一 openid 只保留 A，旧设备可立即解析到新身份。
2. **订单迁移**：B 的全部订单 `memberId → A._id`、`memberName → A.name`；A 自身历史订单的 `memberName` 归一为 A.name；finalize 前再扫描一次 B 残留订单。只改引用，不删除订单、不做同日同菜去重。
3. **个人统计**：逐菜单用 2 文档事务合并 `lunch_user_menu_stats`，`count` 相加、`lastAt` 取较新值，删除 B 的旧统计；重试不重复累计。
4. **月度统计**：服务端复用 `monthStats.js`（lunch_order / lunch_menu 相同副本）定向重建本次迁移 confirmed 订单涉及的月份；重试时按 A 名下全部 confirmed 月份重建（超集）。`dataTimestamp` 原为 0 时走全量重建。
5. **时间戳与 finalize**：更新 `membersTimestamp`、`ordersTimestamp`，统计重建成功时更新 `dataTimestamp`；随后设置 `isVirtual=false`、清除 `mergeFromMemberId`。这些步骤完成前不返回成功。
6. **审计**：审计日志失败只记录错误，不影响合账成功。

**恢复**：`mergeFromMemberId` 是持久化指针。进行中合账会阻止 `deleteMember`、`importMembers`、`rebuildOrderRelations`；管理页成员编辑弹窗显示“继续完成合账”，自助用户可从虚拟成员列表继续。备份恢复会连同指针一起恢复，恢复后的 `dataTimestamp=0` 会走全量统计重建。

**唯一完成条件**：`mergeFromMemberId` 不存在、`isVirtual=false`、`openid` 有值。

### 9.6 requestGate 与安全边界

`requestGate.js` 在每个云函数各有一份副本（`security.test.cjs` 校验一致性），负责：

| 能力 | 行为 |
|------|------|
| 写请求租约 `enter(db, groupId)` | 事务内检查组织存在、`restoreJob` 不存在；把 `activeRequests[token] = now + 120s` 写入组文档；返回 release 函数。恢复期间写请求返回 423 |
| 读请求跳过租约 | 各云函数 `READ_ACTIONS` 集合中的 action 不获取租约，避免与事务/恢复互相阻塞 |
| 恢复维护态 `maintenanceMember` | 组织有 `restoreJob` 时，只有创建者或恢复发起者可继续读取初始化数据，并收到“组织正在恢复备份”的提示 |
| 组 ID 校验 `validGroupId` | 只允许 `[a-zA-Z0-9_-]{1,128}` |
| 导入文件归属 `validImportFile` | fileID 必须为 `cloud://.../lunch/imports/{groupId}/{name}.csv|xlsx`，防止跨组织导入 |
| 原子读取 `optionalDocument` | 文档不存在时返回 null，其他错误继续抛出，用于恢复计划中的存在性判断 |

其他安全/一致性机制：

- **下单幂等锁**：`submitOrder` 以 `sha256(groupId,date,memberId,menuId)` 生成 `lunch_order_keys` 文档，在事务中检查并写入订单，避免同一人同一菜重复提交。
- **审计日志**：成员改名/删除/合并、菜单增删改/显隐、导入等写操作写 `lunch_audit_logs`，含旧值/新值；`expireAt` 约 2 年，失败不阻断主流程。
- **实例级限流**：`lunch_menu` / `lunch_order` / `lunch_backup` 为 30 次/10 秒/openid；`lunch_voice` 为 5 次/10 秒/openid + 30 次/天/openid（`lunch_voice_usage`）。限流是实例内 Map，冷启动会重置，只用于抑制短时异常刷量。
- **下载/导出隔离**：导出与备份文件路径均带 `groupId`，备份元数据按 `groupId` 查询；恢复时还会校验目标文档 `groupId`，禁止覆盖其他组织数据。

## 十二、数据备份

| 类型 | 触发方式 | 保留策略 |
|------|---------|---------|
| 自动备份 | `weeklyBackup` 定时触发器（每周日 02:00，遍历所有组织）+ 管理员手动调用 | 每组织保留最近 8 条 |
| 手动备份 | 管理员点击 | 每组织保留最近 10 条 |
| 安全快照（safety） | 每次恢复开始前自动创建 | 独立保留，不参与普通轮换 |

备份格式为 `version: 2`，内容包含订单、菜单、成员、个人统计、月度统计和下单锁，写入云存储 JSON 文件；`lunch_backups` 文档只存元数据、`fileID` 和 `sha256`。

`lunch_backup` 额外提供：
- `restoreBackup`：`restoreProtocol=2` 分片恢复。先创建安全快照 → 生成恢复计划文件 → 每批 15 条在事务中写入 → 完成后清空 `restoreJob`、把四个时间戳更新为当前时间、`dataTimestamp=0`
- 恢复期间 `requestGate` 让该组织进入维护状态：写请求返回 423，读请求可拿到维护提示；恢复失败保留维护锁，可继续同一备份
- `getBackupCapabilities` 返回协议版本，前端据此拒绝旧协议
- `deleteBackup` 删除备份文档及云存储文件
- `clearAllData`：仅创建者可清空订单、菜单、非创建者成员、月度统计、个人统计、审计日志和下单锁；完成后更新 `orders/menu/members` 时间戳、`dataTimestamp=0`，前端同时重置本机统计缓存与 `statsLoadTime`

## 附录 A：运行形态与平台范围决策（2026-06-21 记录）

> 本节为项目组明确的**非技术方案选择**，用于约束后续实施范围，避免跨平台适配引入不必要的复杂度。

### A.1 当前运行形态

| 平台 | 状态 | 说明 |
|---|---|---|
| 微信小程序（mp-weixin） | **主形态，生产使用** | 云函数走微信云开发；客户端不直接访问数据库，也不使用 `Collection.watch` |
| H5（含 SSR） | **保留构建脚本，不部署** | `package.json` 中的 `build:h5` / `build:h5:ssr` 仅作为潜在能力保留 |
| 其他小程序端（支付宝/百度/京东等） | **不支持** | 仅保留 `dev:` 脚本占位，无适配计划 |

**结论（2026-06-21 确认）：当前仅微信小程序上线，不做 H5 部署。** 本决策可能随业务诉求变化而调整，变更时需更新本节。

### A.2 本地存储范围约定

- 前端存储走 `uni.setStorageSync / getStorageSync`（小程序端落到微信本地存储），**不做跨浏览器/跨设备同步**
- `localStorage` 仅存缓存（菜单、成员、近期订单、时间戳、会话 ID），**核心数据以云端为准**
- 切浏览器 / 切设备 / 重装小程序后，首次打开由 `getInitData` 重建缓存；后续进入走 freshness check 增量更新（见第 8 章）

### A.3 H5 如需上线时的改动清单（保留但不实施）

若未来需要以 H5 形式上线（浏览器网页访问），需补齐以下改动：

1. **`src/services/cloudClient.ts` 统一封装**：当前客户端只通过云函数访问业务数据，不直接访问数据库；H5 端保留同样的云函数访问模型，无需迁移 `watch`
2. **条件编译隔离**：用 `#ifdef MP-WEIXIN` / `#ifdef H5` 分平台分支，避免串用
3. **部署路径**：`npm run build:h5` → 产物上传 CloudBase 静态网站托管（或对象存储 CDN），配置安全域名白名单
4. **登录链路**：H5 端匿名登录 / 微信网页授权登录与小程序端不同，需在 `baseRepository.ts` / `appInit.ts` 加 H5 分支
5. **文件下载**：H5 端 `uni.downloadFile` + `uni.saveFile` 与小程序行为不同，导出 CSV 的下载流程需单独适配

**以上改动当前不实施，仅作为未来决策变更时的启动清单保留。**
