## 七、大数据量与成本优化策略

### 7.1 关键洞察

99% 的使用场景是当天点餐。核心结论：日常操作主要看当天数据，加载最近订单；历史数据在统计页按需加载。

### 7.2 三层加载架构

```
┌─────────────────────────────────────────────────┐
│  第一层：近期数据（每次启动必加载）                │
│  - 近期订单 max(100, 今日记录数)                  │
│  - 菜单列表、成员列表                             │
│  - 当月汇总、notice、多个时间戳                   │
│  → 1次云函数 getInitData                          │
├─────────────────────────────────────────────────┤
│  第二层：月度统计（统计页按需加载）                 │
│  - monthly_stats 全量/增量刷新                    │
│  → getMonthlyStats                               │
├─────────────────────────────────────────────────┤
│  第三层：历史详单（筛选/导出时按需加载）            │
│  - 按筛选条件从云端查询                            │
│  → searchOrders / exportOrders / getHistoryOrders │
└─────────────────────────────────────────────────┘
```

**`getInitData` 内部执行：**
1. 当月聚合（aggregate）→ 返回 `count`，不返回金额
2. 今日订单数 count
3. 近期订单（limit = max(100, todayCount)）
4. 菜单列表 + 大众/个人点餐统计合并（价格字段默认下发，但前端点餐页面不展示）
5. 成员列表
6. 返回时间戳 + notice

### 7.3 实时同步保障

| 机制 | 触发方式 | 说明 |
|------|---------|------|
| **实时监听** | `watchTodayOrders` | 所有在线成员首页均监听今日订单变化；管理员进入管理页也会监听 |
| **自动刷新** | 首页 onShow（每5分钟检查） | 超时后自动检查 todayTimestamp |
| **下拉刷新** | 用户手动下拉 | 强制调用 getRecentOrders |
| **写后即时** | 他人提交订单后 | watch 立即推送，或下次 onShow 同步 |

### 7.4 与账本策略的对比

| 维度 | 账本 | 点餐 |
|------|------|------|
| 默认加载范围 | 全量 records | 最近订单 + 当月聚合 |
| 历史数据 | 渐进式加载+本地缓存 | 按需从云端查询 |
| 实时同步 | `checkDataFreshness`（轮询） | `watchTodayOrders` + 时间戳检查 |
| 统计数据 | local/cloud 双模式 | 统一用 monthly_stats |
| 分片存储 | 需要 | 不需要 |

**关于实时同步的说明：**

- `checkDataFreshness` 是轮询机制，定时请求时间戳/check 接口。优点是稳定可靠、不依赖长连接；缺点是存在轮询间隔延迟，不是真正实时，且会增加云函数调用次数。
- `watchTodayOrders` 是数据库实时推送，数据变更时通常秒级通知客户端。优点是真实时、云函数调用少；缺点是 watch 长连接可能断连、后台/切页面时可能漏事件，需要配合时间戳检查作为兜底。
- **哪个更 robust？** 单论"数据最终一致的保证"，轮询更 robust，因为它不依赖长连接，每次检查都能发现变化。watch 更快，但单独使用不够可靠。当前点餐方案采用 "watch 主实时 + 时间戳检查兜底"，在大部分场景下既实时又可靠；若对实时性要求极高，可再缩短时间戳检查间隔或关键操作后主动触发检查。

### 7.5 点餐程序的时间戳检查机制

**与 `checkDataFreshness` 的区别：**

| 维度 | 账本 `checkDataFreshness` | 点餐时间戳检查 |
|------|------------------------|--------------|
| 性质 | 一个综合检查函数，通常检查整个数据集/多个集合 | 分散的多时间戳对比，每种数据独立检查 |
| 检查对象 | 可能是全局时间戳、版本号或 hash | `recentTimestamp`（订单）、`menuTimestamp`（菜单）、`membersTimestamp`（成员）、`dataTimestamp`（月度统计）、`noticeUpdatedAt`（通知） |
| 触发方式 | 页面 onShow、写操作后等固定时机 | 按数据类型和页面按需触发 |
| 粒度 | 粗粒度，可能一次检查刷新多项 | 细粒度，只刷新发生变化的数据 |

**点餐程序各时间戳的检查时机：**

| 时间戳 | 对应数据 | 检查触发时机 | 处理动作 |
|--------|---------|-------------|---------|
| `recentTimestamp` | 近期订单 | 首页 `onShow`（10 秒节流）、下拉刷新 | 不一致则调用 `getRecentOrders` 重拉 |
| `menuTimestamp` | 菜单列表 | 菜单页 `onShow` | 不一致则调用 `getMenuList` 重拉 |
| `membersTimestamp` | 成员列表 | 菜单页 `onShow`（与菜单时间戳一起检查） | 不一致则调用 `getMembers` 重拉 |
| `dataTimestamp` | 月度统计 | 统计页 `loadStats` | 为 0 时触发全量重建，非 0 时按 `since` 增量刷新 |
| `noticeUpdatedAt` | 通知公告 | 首页 `onShow`、实时监听 `watchGroupNotice` | 今日有效通知则展示，0 点过期清空 |

**关键规则：**
- 写操作（如下单、确认、取消）**不更新自己的本地时间戳**。这样自己下次检查时会因"本地旧时间戳 < 服务端新时间戳"而重新拉取最新数据；其他用户亦然——服务端时间戳已被写操作更新，而他们本地仍保留旧时间戳，下次检查时同样会触发同步
- 时间戳检查作为 `watch` 的兜底：即使 watch 断连或漏事件，用户切换页面时仍能同步到最新数据
- 不同页面只检查与本页相关的时间戳，避免不必要的云函数调用

### 7.6 watch 断连风险与应对

**watch 一般什么时候会断连？**

微信小程序数据库 `watch` 的长连接没有官方固定的超时时间，实际使用中常见断连场景：

| 场景 | 大致情况 |
|------|---------|
| 小程序切后台 | 通常 5 分钟左右可能被系统/微信客户端断开 |
| 网络切换 | WiFi ↔ 移动数据切换、弱网重连 |
| 长时间无数据变更 | 服务端或客户端可能回收空闲连接 |
| 微信进程被清理 | 手机内存不足时微信被杀，再次进入小程序需重建 |

**当前代码已有的恢复机制：**

- `watchTodayOrders` / `watchGroupNotice` 内部会先 `close` 再创建新 watcher
- 首页/管理页 `onShow` 都会重新调用 watch，因此用户从后台切回页面时会重建连接
- 重建后首次 `snapshot.type === 'init'` 的数据被忽略，避免重复渲染

**是否需要定时重启 watch？**

可以但通常没必要。定时重启（如每 3-5 分钟 close 再 watch）能减少"页面长期前台但连接已断"的窗口期，但代价是：

- 每次重建会触发一次初始化快照，产生数据库读和网络开销
- 增加耗电，尤其在低端机上
- 当前点餐场景下，用户切页面较频繁，且有时间戳检查兜底

**建议策略：**
- 保持现状：`onShow` 重建 + 时间戳兜底
- 若管理员首页对实时性要求极高，可在 `onShow` 时立即调用一次 `getRecentOrders`/`loadData`，而非等待 watch 推送
- 不要设置高频定时重启，避免不必要的资源消耗

## 八、缓存与云函数调用策略

### 8.1 核心原则

> TCB 不限制数据库读写次数，只限制云函数调用次数和响应体大小。优化优先级：
> 1. 尽量少调用云函数
> 2. 数据不经过前端中转
> 3. 写操作不更新自己的本地时间戳，下次检查时能发现服务端已更新
> 4. 自己的写操作不更新自己的本地时间戳 — 你下次检查时会因"本地旧时间戳 < 服务端新时间戳"而重拉；别人也一样，他们本地时间戳仍是旧的，服务端时间戳已被你的写操作更新，下次检查时同样会触发同步。**你永远不能改别人的本地时间戳，只有服务端时间戳是大家共同对比的基准。**
> 5. 外部批量导入/清库重写时，通过更新时间戳或清零 `dataTimestamp` 让前端感知变化
> 6. 当天数据优先，历史按需加载

### 8.2 缓存架构

```
Vue 3 Reactive State
    ↓
内存缓存标志 + 时间戳
    ↓
本地持久化存储（uni.getStorageSync / localStorage）
```

### 8.3 新鲜度检查策略

```
首页 onShow：
  1. 5分钟内已检查 → 跳过
  2. 超过5分钟 → getRecentTimestamp
     ├─ 时间戳一致 → 结束
     └─ 时间戳不一致 → getRecentOrders
  3. 下拉刷新 → 强制忽略缓存 → getRecentOrders
```

菜单/成员列表通过 `menuTimestamp` / `membersTimestamp` 感知变化，避免重复全量拉取。

### 8.4 写操作策略

复用账本核心规则：**写操作不更新自己的本地 `_recentTimestamp`**。

```
提交订单流程：
1. 调用云函数 submitOrder → 服务端 ordersTimestamp 更新
2. 本地 state.recentOrders.push（即时显示）
3. 持久化到 localStorage
4. 自己的 _recentTimestamp 保持旧值 ← 关键！

5分钟后 onShow → getRecentTimestamp：
  → 自己的旧时间戳 ≠ 服务端新时间戳 → 重新拉最近订单
```

> 为什么不能更新自己的本地时间戳？
> 如果写完后把本地时间戳也改成最新，下次 `checkFreshness` 就会发现"本地 == 服务端"，跳过拉取，导致自己看不到服务端的真实最新状态（比如其他人在你写操作之后提交的数据）。保持旧值，才能强制下次检查触发同步。
>
> 其他用户如何看到我的变化？他们本地也保留着自己的旧时间戳，我写操作更新了服务端时间戳，他们下次检查时也会触发同步。

### 8.5 外部导入/清库场景下的时间戳策略

所有外部数据导入（管理页上传 CSV/XLSX）**必须走云函数**，由云函数负责更新时间戳。直接绕过云函数修改数据库，前端无法感知。

| 导入操作 | 数据集合 | 更新的时间戳 | 是否清零 `dataTimestamp` | 说明 |
|---------|---------|------------|----------------------|------|
| `importOrders` 追加/重写 | `lunch_orders` | `ordersTimestamp` | 是（仅最后一批 `isLastBatch=true`） | 影响月份不确定，全量 rebuild |
| `importMembers` 追加 | `lunch_members` | `membersTimestamp` | 否 | 不影响历史统计 |
| `importMembers` 清库重写 | `lunch_members` | `membersTimestamp` | 是 | 成员/虚拟成员可能关联历史订单 |
| `importMenuItems` 追加/重写 | `lunch_menu` | `menuTimestamp` | 否 | 菜单不影响已有订单的 supplier/price |

清零 `dataTimestamp` 的含义：标记"月度统计需要全量重建"。下次访问统计页时，`getMonthlyStats` 检测到 `dataTimestamp === 0`，先占位更新，再自动重建 `lunch_monthly_stats`。

### 8.6 冷启动恢复

```
App onLaunch → restoreSession() → restoreFromCache()：
1. 从 localStorage 读取 members / menu / recentOrders / 时间戳
2. 直接填充 state
3. 用户立即看到上次数据
4. 首次 onShow → 后台静默验证并更新
```

### 8.7 统计页加载策略

```
进入统计页：
  1. 检查 monthlyStats 缓存
     ├─ 有缓存且未过期 → 直接用，同时 getMonthlyStats(since) 增量刷新
     └─ 无缓存或过期 → getMonthlyStats（可能触发全量重建）
  2. 筛选变更 → 前端 computed 过滤
  3. 查看详单 → searchOrders
  4. 下载 → downloadMonthlyData
```

`getMonthlyStats` 内部逻辑：
- `dataTimestamp === 0` → 立即占位更新 + 全量重建 + 返回全量
- 有 `since` 参数 → 返回增量变更；无变更时返回空数组 + incremental=true
- 无 `since` → 查询全部；若某月 `updatedAt < dataTimestamp` 则单独重建

### 8.8 关于"缓存永久有效"的说明

`cacheConfig.ts` 中时间戳缓存 TTL = 0，**仅表示本地存储的时间戳不会因"过期"被自动丢弃**，不是说数据永远不刷新。

实际是否刷新，取决于**服务端时间戳与本地时间戳是否一致**：

```
本地时间戳 = 服务端时间戳  →  跳过，不刷新
本地时间戳 ≠ 服务端时间戳  →  触发对应数据的重拉/重建
```

因此：
- 外部批量导入/清库重写时，**服务端时间戳必须被更新**，前端才能感知
- `importOrders` 在最后一批清零 `dataTimestamp`，就是让"本地旧值 ≠ 服务端 0"，从而触发统计页重建
- 如果绕过云函数直接改数据库，前端的时间戳对比会失效，缓存将长期过期

### 9.3 月度统计重建（核心防并发设计）

```javascript
// doRebuildMonthStats 关键实现
async function doRebuildMonthStats(targetYearMonth) {
    // 1. 清除旧记录
    await db.collection('lunch_monthly_stats').where(statsWhere).remove()

    // 2. 拉取 confirmed 订单并聚合
    const monthMap = {}
    // ... 聚合计算 ...

    // 3. 用确定性 _id 写入，避免并发重复

    await db.collection('lunch_monthly_stats').doc(docId).set({ data: { ... } })

```

`getMonthlyStats` 中 `dataTimestamp === 0` 时先 `_updateDataTimestamp()` 占位，防止并发请求重复重建。

### 9.4 导入数据（importOrders / importFromXlsx）

**模式：**
- `rewrite`：清空现有订单后导入
- `append`：追加导入，仅对最近一天做去重

**自动创建：**
- 缺失成员 → 创建 `isVirtual=true` 的虚拟成员
- 缺失菜品 → 使用 CSV 数据中的 supplier/price 自动创建

**批量处理：**
- 每批 ≤100 条插入
- 仅最后一批通过 `isLastBatch=true` 重置 `dataTimestamp=0`
- 返回 `{ count, errors, skipped, skippedDetails }`，不返回完整 results 数组（避免超 1MB）

**导入操作的时间戳更新（与 8.5 节对照）：**

| 导入操作 | 云函数 | 时间戳更新 | `dataTimestamp` 清零 |
|---------|--------|-----------|-------------------|
| `importOrders` | `lunch_order` | 每批结束更新 `ordersTimestamp` | 仅最后一批 `isLastBatch=true` |
| `importFromXlsx` | `lunch_order` | 单次结束更新 `ordersTimestamp` | 默认 `isLastBatch=true` |
| `importMembers` rewrite | `lunch_menu` | 更新 `membersTimestamp` | 是 |
| `importMembers` append | `lunch_menu` | 更新 `membersTimestamp` | 否 |
| `importMenuItems` rewrite/append | `lunch_menu` | 更新 `menuTimestamp` | 否 |

所有导入完成后，服务端时间戳已经改变，前端在下次 `onShow` / `loadStats` 时即可感知并刷新。

### 9.5 云函数超时配置


所有云函数统一配置 20 秒超时。

```typescript
// useRealtimeWatch.ts 增强
function watchTodayOrders(onChange: (snapshot: any) => void) {
    closeOrderWatcher()
    const db = wx.cloud.database()
    orderWatcher = db.collection(COLLECTIONS.ORDERS)
        .where({ groupId: GROUP_ID, date: getToday() })
        .watch({
            onChange: (snapshot) => {
                if (snapshot.type === 'init') {
                    onChange({ type: 'init', docs: snapshot.docs })
                    return
                }
                onChange({ type: 'changes', changes: snapshot.docChanges || [] })
            },
            onError: (err) => { /* 见 O8 */ }
        })
}

// useHome.ts 调用方
realtime.watchTodayOrders((payload) => {
    if (payload.type === 'init') return // 已有 loadInitData
    const orders = [...store.recentOrders]
    for (const c of payload.changes) {

        if (t === 'add' && idx < 0) orders.unshift(c.doc)
        else if (t === 'update' && idx >= 0) orders[idx] = c.doc
        else if (t === 'remove' && idx >= 0) orders.splice(idx, 1)

    setStore({ recentOrders: orders })
```

#### O8. watch onError 降级 + 退避重建（已实施，2026-06-21）

**问题核对**（已确认）：
- `useRealtimeWatch.ts:26-29` onError 仅 `console.error + orderWatcher = null`
- 断连后到下次 onShow 之间，用户看到过期数据

**更优解**：保留 v2.0 方案，补充指数退避：

```typescript
function watchTodayOrders(onChange, onFallback) {
    let retryCount = 0
    let retryTimer: any = null

    const start = () => {
        orderWatcher = db.collection(COLLECTIONS.ORDERS)
            .where({ groupId: GROUP_ID, date: getToday() })
            .watch({
                onChange,
                onError: (err) => {
                    console.error('[watch] error:', err)
                    orderWatcher = null
                    onFallback?.() // 立即兜底拉取
                    // 指数退避：30s, 60s, 120s, 最大 5 分钟
                    const delay = Math.min(30000 * Math.pow(2, retryCount++), 300000)
                    retryTimer = setTimeout(start, delay)
                },
            })
    }
    start()

    return {
        close: () => {
            if (retryTimer) clearTimeout(retryTimer)
            orderWatcher?.close()
            orderWatcher = null
        }
    }
}
```

**前后对比**：

| 维度 | 优化前 | 优化后 |
|------|--------|--------|
| 断连后恢复方式 | 等下次 onShow | 30s 后自动重建 |
| 断连期间数据 | 过期 | 立即兜底拉取 1 次 |

#### O19. setCache 同步写阻塞（新增，已实施，2026-06-21）

**问题核对**：

- 导入大批量数据时，每条记录都触发 setCache，阻塞 UI

**更优解**：防抖 + 批量写：

```typescript
const pendingWrites = new Map<string, any>()
let writeTimer: any = null

export function setCache(key: string, data: any) {
    pendingWrites.set(key, data)
    if (writeTimer) clearTimeout(writeTimer)
    writeTimer = setTimeout(flushWrites, 500)
}

function flushWrites() {
    for (const [key, data] of pendingWrites) {
        uni.setStorageSync(key, JSON.stringify({ data, ts: Date.now() }))
    }
    pendingWrites.clear()
    writeTimer = null
}
```

| 导入 2000 条 setCache 调用 | 2000 次同步写 | 1 次（防抖后） |
| UI 阻塞 | 明显 | 无 |

**落地步骤**：
1. store.ts 增加 pendingWrites + writeTimer
2. setCache 改为防抖
3. 关键路径（如 saveSession）提供 forceFlush 选项

## 附录 A：运行形态与平台范围决策（2026-06-21 记录）

> 本节为项目组明确的**非技术方案选择**，用于约束后续实施范围，避免跨平台适配引入不必要的复杂度。

### A.1 当前运行形态

| 平台 | 状态 | 说明 |
|---|---|---|
| 微信小程序（mp-weixin） | **主形态，生产使用** | 云函数走微信云开发，实时监听走 `wx.cloud.database().watch()` |
| H5（含 SSR） | **保留构建脚本，不部署** | `package.json` 中的 `build:h5` / `build:h5:ssr` 仅作为潜在能力保留 |
| 其他小程序端（支付宝/百度/京东等） | **不支持** | 仅保留 `dev:` 脚本占位，无适配计划 |

**结论（2026-06-21 确认）：当前仅微信小程序上线，不做 H5 部署。** 本决策可能随业务诉求变化而调整，变更时需更新本节。

### A.2 本地存储范围约定

- 前端存储走 `uni.setStorageSync / getStorageSync`（小程序端落到微信本地存储），**不做跨浏览器/跨设备同步**
- `localStorage` 仅存缓存（菜单、成员、近期订单、时间戳、会话 ID），**核心数据以云端为准**
- 切浏览器 / 切设备 / 重装小程序后，首次打开由 `getInitData` 重建缓存；后续进入走 freshness check 增量更新（见第 8 章）

### A.3 H5 如需上线时的改动清单（保留但不实施）

若未来需要以 H5 形式上线（浏览器网页访问），需补齐以下改动：

1. **`src/services/cloudClient.ts` 统一封装**：当前实时监听直接走 `wx.cloud.database().watch()`，H5 端需切换为 `@cloudbase/js-sdk` 并处理 `watch` 在 Web SDK 下的接口差异
2. **条件编译隔离**：用 `#ifdef MP-WEIXIN` / `#ifdef H5` 分平台分支，避免串用
3. **部署路径**：`npm run build:h5` → 产物上传 CloudBase 静态网站托管（或对象存储 CDN），配置安全域名白名单
4. **登录链路**：H5 端匿名登录 / 微信网页授权登录与小程序端不同，需在 `baseRepository.ts` / `appInit.ts` 加 H5 分支
5. **文件下载**：H5 端 `uni.downloadFile` + `uni.saveFile` 与小程序行为不同，导出 CSV 的下载流程需单独适配

**以上改动当前不实施，仅作为未来决策变更时的启动清单保留。**
