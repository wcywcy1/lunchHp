## 七、大数据量与成本优化策略

### 7.1 关键洞察：99% 的使用场景是当天点餐

| 使用场景 | 频率 | 数据范围 | 操作人 |
|---------|------|---------|--------|
| 看今日点单 | 每天数十次 | 近期订单 | 所有人 |
| 点餐下单 | 每天20次 | 仅当天 | 所有人 |
| 确认订单 | 每天1次 | 仅当天 | 管理员 |
| 看历史统计 | 偶尔 | 全量 | 管理员为主 |
| 导出/下载 | 极少 | 全量 | 管理员 |

**核心结论：日常操作主要看当天数据，但为保险起见加载最近100条（约5个工作日），历史数据在统计页按需加载。**

### 7.2 优化策略：按需加载，而非全量加载

与账本不同，账本用户经常翻看历史记录，所以需要全量加载+渐进式追加。
点餐场景**不需要**这套复杂机制，可以大幅简化：

```
账本策略：启动 → 全量加载 → 增量同步 → 渐进追加
点餐策略：启动 → 加载近期订单 → 历史数据按需拉取
```

**三层加载架构：**

```
┌─────────────────────────────────────────────────┐
│  第一层：近期数据（每次启动必加载）                │
│  - 近期订单 max(100, 今日记录数)                  │
│    → 保证当天数据一定完整，额外带几天历史          │
│  - 菜单列表（≤50条）                              │
│  - 成员列表（≤30条）                              │
│  - 当月汇总（云端实时聚合，见下方说明）            │
│  → 1次云函数 getInitData 合并返回                  │
│  → 覆盖 99% 的日常使用场景                        │
├─────────────────────────────────────────────────┤
│  第二层：月度统计（统计页按需加载）                 │
│  - monthly_stats 全量缓存                         │
│  - 仅在进入统计页时检查/加载                       │
│  → 0~1次云函数 getMonthlyStats                    │
│  → 管理员偶尔使用                                 │
├─────────────────────────────────────────────────┤
│  第三层：历史详单（筛选/导出时按需加载）            │
│  - 按筛选条件从云端查询                            │
│  - 不缓存到本地（历史数据不可变，无需缓存）         │
│  → 1次云函数 searchOrders / exportOrders          │
│  → 极少使用                                       │
└─────────────────────────────────────────────────┘
```

**首页只显示当天点单**，recentOrders 中的历史数据供菜单页/数据页参考，不在首页列表展示。

**首页"当月总金额"的数据来源：**

recentOrders 无法覆盖整月（20人×22天≈440条/月），不能本地聚合。
解决方案：**getInitData 内部用 db.aggregate 实时聚合当月数据**。

```
getInitData 云函数（lunch_order）内部执行：
  1. db.collection('lunch_orders')
     .where({ groupId, date: db.RegExp({ regexp: '^2026-06' }) })
     .aggregate() → sum(price), count()          ← 当月汇总（首页用）
     
  2. db.collection('lunch_orders')
     .where({ groupId, date: today })
     .count()                                     ← 今日记录数
     
  3. db.collection('lunch_orders')
     .where({ groupId })
     .orderBy('createdAt', 'desc')
     .limit(max(100, todayCount))                ← 近期订单，保证当天完整
     
  4. db.collection('lunch_menu')
     .where({ groupId })
     .orderBy('sortNo', 'asc')
     .get()                                       ← 菜单列表
     
  5. db.collection('lunch_members')
     .where({ groupId })
     .get()                                       ← 成员列表
     
  6. 返回 recentTimestamp                         ← 新鲜度检查用

  合并返回：{ monthSummary, recentOrders, menu, members, recentTimestamp }
```

**为什么这样不牺牲性能：**
- TCB **不限制数据库读写次数**，只限制云函数调用次数
- getInitData 内部6次 db 查询 = 1次云函数调用
- aggregate 聚合是数据库引擎执行，速度极快（毫秒级）
- 当月数据量 ≤440条，聚合计算量极小
- 结果随 recentOrders 一起返回，无额外网络开销
- `max(100, todayCount)` 保证当天数据一定完整，正常情况100条足够

### 7.3 实时同步保障：管理员不会漏掉新订单

| 机制 | 触发方式 | 说明 |
|------|---------|------|
| **自动刷新** | 首页 onShow（每5分钟检查） | 超时后自动检查 todayTimestamp，有新数据则拉取 |
| **下拉刷新** | 用户手动下拉 | 强制调用 getRecentOrders，立即获取最新数据 |
| **写后即时** | 他人提交订单后 | 下次 onShow 或下拉即可看到 |

**下拉刷新流程：**
```
用户下拉 → 强制忽略缓存时间 → getRecentOrders（1次云函数）→ 更新 state + localStorage
```

**管理员场景：**
```
1. 管理员打开首页 → 看到当前所有已提交订单
2. 张三刚提交了一个红烧肉 → 管理员下拉刷新 → 立即看到张三的订单
3. 不下拉 → 最多5分钟后自动检查也会同步到
```

### 7.4 与账本策略的对比

| 维度 | 账本 | 点餐 | 原因 |
|------|------|------|------|
| 默认加载范围 | 全量 records | 最近100条 orders | 点餐主要看当天 |
| 历史数据 | 渐进式加载+本地缓存 | 按需从云端查询 | 历史不可变，无需缓存 |
| 统计数据 | local/cloud 双模式 | 统一用 monthly_stats | 不需要 local 模式 |
| 增量同步 | checkDataFreshness | 仅检查近期数据 | 历史不会变 |
| 分片存储 | 需要（规避1MB限制） | 不需要 | 100条数据极小 |
| 冷启动恢复 | 全量 localStorage | 最近100条 | 恢复更快 |
| 下拉刷新 | 有 | 有 | 管理员实时查看新订单 |

### 7.5 复用账本的部分

| 复用项 | 来源 | 说明 |
|--------|------|------|
| baseRepository 模式 | 账本 baseRepository.js | cloudAction 调度器，复制源码到新项目 |
| cloudClient | 账本 cloudClient.js | 复制源码，**改为新环境ID**初始化 |
| monthly_stats | 账本 RevD_stats | 云端聚合 + 增量刷新 + 本地缓存 |
| 导出 CSV | 账本 useDataExport.js | 改表头即可 |
| FilterPanel | 账本 FilterPanel.vue | FAB + 底部弹出面板 |
| CheckboxPicker | 账本 CheckboxPicker.vue | 多选选择器 |

### 7.6 不复用（简化）的部分

| 账本功能 | 点餐处理 | 原因 |
|---------|---------|------|
| 全量加载 + 渐进追加 | 仅加载当天 | 日常只看当天 |
| local/cloud 双模式 | 统一 cloud 模式 | 统计一律走 monthly_stats |
| 分片存储 | 不需要 | 当天数据 ≤20条 |
| checkDataFreshness 增量同步 | 仅刷新当天 | 历史不可变 |
| 拉手逻辑（追加1500条） | 不需要 | 按需查询替代 |
| dataTimestamp + sinceTimestamp | 当天数据时间戳 | 只关心当天是否有新订单 |

## 八、缓存与云函数调用策略

### 8.1 核心原则

> **TCB 不限制数据库读写次数，只限制云函数调用次数和响应体大小。优化优先级：**
> 1. 尽量少调用云函数
> 2. 数据不经过前端中转
> 3. 写操作不更新本地时间戳（保障多人同步）
> 4. **当天数据优先，历史按需加载**

### 8.2 缓存架构

```
┌─────────────────────────────────────────────┐
│            Vue 3 Reactive State             │
│  state.recentOrders / state.menu / ...      │  ← 最近100条订单
│  state.monthlyStats / state.members         │
└──────────────┬──────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────┐
│         内存缓存标志 + 时间戳                 │
│  _recentLoaded / _menuLoaded / ...          │
│  _recentLoadTime / _menuLoadTime / ...      │
│  _recentTimestamp                           │  ← 近期数据的时间戳
└──────────────┬──────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────┐
│         本地持久化存储                        │
│  MP: wx.setStorageSync / wx.getStorageSync  │
│  H5: localStorage                           │
│  lunch_cache_recent_orders ← 最近100条，无需分片│
│  lunch_cache_menu                              │
│  lunch_cache_members                           │
│  lunch_cache_monthly_stats ← 全量缓存          │
│  lunch_session                                 │
└─────────────────────────────────────────────┘
```

### 8.3 各数据缓存配置

| 数据类型 | 缓存有效期 | 持久化 key | 说明 |
|---------|-----------|-----------|------|
| members | 30分钟 | `lunch_cache_members` | 成员极少变动 |
| menu | 30分钟 | `lunch_cache_menu` | 菜单变化频率低 |
| recentOrders | 5分钟 | `lunch_cache_recent_orders` | 近期订单 max(100,今日记录数)，无需分片 |
| recentTimestamp | — | `lunch_cache_recent_timestamp` | 近期数据时间戳 |
| monthlyStats | 永久（增量刷新） | `lunch_cache_monthly_stats` | 全量缓存所有年份 |
| monthlyStatsTime | — | `lunch_cache_monthly_stats_time` | 缓存时间戳 |
| session | 永久 | `lunch_session` | {groupId, memberId, role} |

**与账本的关键区别：**
- 不缓存全量 orders，只缓存 recentOrders（最近100条）
- 不需要分片存储（100条约10-15KB，远小于1MB）
- 不需要 dataTimestamp + sinceTimestamp 增量同步
- 历史详单不缓存，每次从云端按需查询

### 8.4 新鲜度检查策略（简化版）

```
首页 onShow：
  1. 5分钟内已检查 → 跳过（0次云函数）
  2. 超过5分钟 → getRecentTimestamp（1次云函数）
     ├─ 时间戳一致 → 结束（共1次）
     └─ 时间戳不一致 → getRecentOrders（共2次，重新拉最近100条）
  3. 下拉刷新 → 强制忽略缓存 → getRecentOrders（1次云函数）
```

**与账本的区别：**
- 账本：增量同步（sinceTimestamp 以来新增的记录）
- 点餐：直接重新拉最近100条（响应体约10-15KB，比增量同步更简单可靠）
- 下拉刷新：强制忽略缓存时间，立即拉取最新数据

### 8.5 写操作策略

复用账本核心规则：**写操作不更新 _recentTimestamp**

```
提交订单流程：
1. 调用云函数 submitOrder → 服务端 recentTimestamp 更新
2. 本地 state.recentOrders.push（即时显示）
3. 持久化到 localStorage
4. _recentTimestamp 保持旧值 ← 关键！

5分钟后 onShow → getRecentTimestamp：
  → 本地旧时间戳 ≠ 服务端新时间戳 → 重新拉最近100条 → 获取他人提交的订单
```

### 8.6 冷启动恢复（Stale-While-Revalidate）

```
App onLaunch → restoreSession() → restoreFromCache()：
1. 从 localStorage 读取 members / menu / recentOrders
2. 直接填充 state，标记 loaded=true
3. 恢复 _recentTimestamp
4. 用户立即看到上次数据（可能过时）
5. 首次 onShow → getRecentTimestamp → 后台静默验证并更新
```

**与账本的区别：**
- 恢复更快：只恢复最近100条，而非全量
- 不需要恢复 _cachedTotal（不关心历史总量）

### 8.7 统计页加载策略

```
进入统计页：
  1. 检查 monthlyStats 缓存
     ├─ 有缓存且当天已刷新 → 直接用（0次云函数）
     └─ 无缓存或过期 → getMonthlyStats（1次云函数）
  2. 筛选变更 → 前端 computed 过滤 monthlyStats（0次云函数）
  3. 查看详单 → searchOrders（1次云函数，按筛选条件从云端查询）
  4. 下载 → downloadMonthlyData（1次云函数）
```

### 8.8 各场景云函数调用量

#### 日常使用（点餐者）

| 场景 | 云函数调用 | 说明 |
|------|-----------|------|
| 首页 onShow（5分钟内） | **0次** | 缓存命中 |
| 首页 onShow（>5分钟，数据未变） | **1次** | getRecentTimestamp |
| 首页 onShow（>5分钟，数据有变） | **2次** | getRecentTimestamp + getRecentOrders |
| 首页下拉刷新 | **1次** | getRecentOrders（强制刷新） |
| 菜单页 onShow | **0次** | 菜单30分钟缓存 |
| 提交点餐 | **1次** | submitOrder |
| 看统计（缓存命中） | **0次** | monthlyStats 缓存 |
| 看统计（首次/过期） | **1次** | getMonthlyStats |

#### 日常使用（管理员）

| 场景 | 云函数调用 | 说明 |
|------|-----------|------|
| 同上所有点餐者场景 | 同上 | — |
| 批量确认 | **1次** | batchConfirm |
| 下载确认单 | **1次** | 云函数内生成文件 |
| 导出清单 | **1次** | 云函数内生成CSV |

#### 冷启动

| 场景 | 云函数调用 | 说明 |
|------|-----------|------|
| 登录冷启动（数据未变） | **0次** | applyLoginCache 设置5分钟免检 |
| 缓存恢复冷启动（数据未变） | **1次** | getRecentTimestamp |
| 缓存恢复冷启动（数据有变） | **2次** | getRecentTimestamp + getRecentOrders |
| 首次使用（无缓存） | **1次** | getInitData（合并返回 members+menu+recentOrders+monthSummary） |

**与账本的关键区别：首次使用仅 1 次云函数**（账本需要 2-3 次），因为 getInitData 合并返回所有近期数据。

#### 月度调用量估算（20人，每天使用）

| 操作 | 日均次数 | 云函数/次 | 月均调用 |
|------|---------|----------|---------|
| 首页 onShow | 40次/人×20人=800 | 0.15（85%缓存命中） | **120** |
| 首页下拉刷新 | 5 | 1 | **110** |
| 提交点餐 | 20 | 1 | **600** |
| 批量确认 | 1 | 1 | **22** |
| 看统计 | 5 | 0.2 | **22** |
| 菜单编辑 | 0.5 | 1 | **11** |
| 下载/导出 | 0.2 | 1 | **4** |
| **月合计** | | | **~889次** |

微信云开发免费额度：**5万次/月**，889次仅占 **1.8%**，完全够用。

**与账本方案对比的节省：**
- 首次启动：1次 vs 2-3次
- 日常 onShow：85%缓存命中 vs 80%（近期数据更稳定）
- 不需要增量同步逻辑（直接重拉最近100条）
- 不需要分片存储逻辑

**与账本云函数的关键区别：**
- `getInitData` 合并到 `lunch_order`：首次启动仅需 1 次调用，返回 recentOrders+monthSummary+menu+members+recentTimestamp
- 新增 `initGroup`（在 `lunch_menu` 中）：自动检测并创建 `lunch_groups` 记录，无需手动在控制台初始化
- 新增 `getRecentTimestamp`：仅检查近期数据是否变化，而非全量时间戳
- 新增 `getRecentOrders`：拉取最近100条，支持下拉刷新强制调用
- 去掉 `getOrders`（渐进式加载）：不需要，历史数据按需查询
- 去掉 `getDataTimestamp`（全量时间戳）：替换为 getRecentTimestamp
- `rebuildMonthStats` 触发时机：订单批量确认后自动调用 + 管理员手动触发
- 去掉 `getMonthSummary`：合并到 getInitData 中

### 9.5 TCB 限制遵守

复用账本已验证的安全策略：

| 限制项 | 值 | 应对 |
|--------|-----|------|
| 云函数响应体 | 1MB | 读取返回前端 limit≤1500 |
| 云函数请求体 | 1MB | 批量导入每批≤100条 |
| 云函数内单次查询 | 1000条 | fetchAll 循环分页 |
| 批量插入 | 100条 | 分批100条循环插入 |
| 批量删除 | 无限制 | .where().remove() |
| 云函数超时 | 20秒 | 批量操作注意超时 |

### 11.5 全量导出（大数据量方案）

当数据量超过 1500 条时，前端分页拉取效率低且可能超时。采用**云函数生成文件 + 云存储下载**方案：

```
用户点"导出全量" →
  云函数 exportAllOrders：
    1. fetchAll 循环查询所有 orders（每次 1000 条）
    2. 拼接 CSV 字符串
    3. 上传到云存储 lunch/exports/export_20260616_xxx.csv
    4. 返回 fileID
  前端收到 fileID →
    5. wx.cloud.downloadFile 下载
    6. wx.openDocument 打开
```

**优点：**
- 无论多少条数据，前端只调用 1 次云函数
- 不受 1MB 响应体限制
- 下载走云存储 CDN，速度快
- 临时文件 7 天后自动清理（云函数内设置 TTL 或定时清理）

### 11.6 数据备份

**备份策略：**

| 类型 | 触发方式 | 存储方式 | 保留策略 | 说明 |
|------|---------|---------|---------|------|
| 自动备份 | 定时触发器（每周日凌晨 2 点） | `lunch_backups` 集合，`type=auto` | 保留最近 8 周（约 2 个月），超出自动删除 | 每周自动，不覆盖 |
| 手动备份 | 管理员点击"立即备份" | `lunch_backups` 集合，`type=manual` | 保留最近 10 条，超出删除最旧 | 管理员手动触发 |

**备份集合结构：**

```
lunch_backups（备份元数据）
  _id               // 备份ID，如 backup_20260615_020000
  type              // auto / manual
  createdAt         // 备份时间
  orderCount        // 订单数
  menuCount         // 菜单数
  memberCount       // 成员数
  dateRange         // 数据时间范围 {start, end}
  remark            // 备注（手动备份可填写）
  data              // 备份数据（JSON字符串，包含 orders/menu/members 全量数据）
```

**说明：** 备份数据直接存储在 `lunch_backups` 集合的 `data` 字段中（JSON字符串），不需要为每个备份创建单独的集合。这样管理更简单，恢复时直接读取即可。

**备份列表展示：**

```
┌─────────────────────────────────┐
│  备份历史                        │
├─────────────────────────────────┤
│  🟢 自动备份                     │
│  2026-06-15 02:00  订单:1280     │
│  2026-06-08 02:00  订单:1245     │
│  2026-06-01 02:00  订单:1198     │
│  ...                            │
├─────────────────────────────────┤
│  🔵 手动备份                     │
│  2026-06-16 14:30  订单:1290     │
│  [备注: 大改前备份]               │
│  2026-06-10 09:15  订单:1260     │
│  [备注: ]                        │
└─────────────────────────────────┘
```

**备份内容：**
- `lunch_orders` 全量订单
- `lunch_menu` 全量菜单
- `lunch_members` 全量成员

**恢复流程：**
1. 管理员进入数据页 → 点击"恢复备份"
2. 弹出备份列表（显示所有自动备份 + 手动备份，按时间倒序）
3. 选择某条备份 → 预览备份数据（记录数、时间范围）
4. 确认恢复 → 清空当前数据 → 写入备份数据
5. 恢复前自动创建一次手动备份（防止误操作）

**云函数：**
```
backupAuto     // 自动备份（定时触发器调用）
backupManual   // 手动备份（创建新记录，不覆盖）
restoreBackup  // 恢复备份（选择备份ID）
getBackupList  // 获取所有备份列表（自动+手动，按时间倒序）
deleteBackup   // 删除指定备份（管理员）
```

**定时触发器配置：**
```json
// wxcloud/functions/lunch_backup/config.json
{
  "triggers": [{
    "name": "weeklyBackup",
    "type": "timer",
    "config": "0 0 2 * * SUN"  // 每周日凌晨 2 点
  }]
}
```
