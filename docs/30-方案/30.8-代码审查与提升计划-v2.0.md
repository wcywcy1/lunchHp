## 二、首页模块（useHome + Home 页面）

### 2.1 useHome Hook | 有提升空间

| 项目 | 说明 |
|------|------|
| 设计意图 | 首页数据加载、实时监听、新鲜度检查、用户交互 |
| 改善方案 | A. `checkFreshness` 中 `menuTimestamp` 和 `membersTimestamp` 被更新到 store 和 cache，但 `recentTimestamp` 在 `fetchRecentOrders` 中才更新，逻辑分散。建议统一在 `checkFreshness` 末尾统一 `setStore` 所有时间戳。<br><br>B. `refreshMonthSummary` 在 watch onPatch 和 fetchRecentOrders 中都会调用，但 `getMonthSummary` 云函数每次都要做 aggregate。如果当天订单数变化频繁（如多人同时点餐），会多次触发 aggregate。建议首页 `monthCount` 用本地计算（todayOrders 过滤），只在需要金额时才调用 aggregate。<br><br>C. `onShow` 中 `startRealtimeWatch` 在 `checkFreshness` 之前启动，如果 watch 立即推送变更，`checkFreshness` 可能覆盖本地 patch。建议先 `checkFreshness` 再 `startRealtimeWatch`，或确保 `fetchRecentOrders` 不会与 patch 冲突 |
| 好处 | 运行速度 — 减少不必要的 aggregate；云函数调用 — 减少重复 `getMonthSummary` |

### 2.2 实时监听（useRealtimeWatch）| 有提升空间

| 项目 | 说明 |
|------|------|
| 设计意图 | watchTodayOrders + watchGroupNotice 双监听，指数退避重连 |
| 改善方案 | A. `watchTodayOrders` 的 `onError` 回调触发 `cb.onError`，但 useHome 中 `onError: () => { fetchRecentOrders() }` 会再拉一次全量。如果 watch 频繁断连（如弱网），会形成"断连→重连→又断→又拉"的循环，增加云函数调用。建议增加断连次数阈值，超过 3 次后不再自动拉取，等待下次 onShow。<br><br>B. `watchGroupNotice` 没有指数退避重连机制 — 与 `watchTodayOrders` 不对等，断连后永久丢失通知推送，只能等 onShow 兜底。建议统一加退避重连。<br><br>C. `GROUP_ID` 是硬编码常量，通用模式下会失效 — `useRealtimeWatch.ts` 第 3 行 `import { GROUP_ID }`，但 `baseRepository.ts` 已经支持动态 groupId。watch 应该用 `store.groupId || GROUP_ID` |
| 好处 | 运行速度/云函数调用 — 减少弱网下的无效拉取；功能 — 通知监听也能自动恢复；功能 — 支持通用模式 |

## 六、云函数层

### 6.1 lunch_order（订单+统计+导入导出）| 有提升空间

| 项目 | 说明 |
|------|------|
| 设计意图 | 订单CRUD、统计聚合、批量操作、导入导出 |
| 改善方案 | A. `getInitData` 中 `recentOrders` 的 limit = max(100, todayCount)，上限 500。如果今天有 200 单，会拉 200 条。但 `getTodayString()` 用的是云函数本地时间（服务器时间），如果前端和服务器时区不一致，"今天"可能不一致。建议用 `db.serverDate()` 获取服务器时间。<br><br>B. `_autoCancelExpiredPending` 用 `Date.now()` 做节流（60秒），但 `getToday()` 用的是 `new Date()` 本地时间，如果云函数实例时区不是中国时区，"今天"会错。建议明确用东八区时间。<br><br>C. `submitOrder` 中查重只查 `status: PENDING`，但如果用户今天已经有一个 `confirmed` 订单，又点了一个 `pending`，这是允许的。需要确认需求是否允许一人一天多点。一般点餐小程序一人一天只点一次，建议增加限制。<br><br>D. `batchConfirm` 中 `updateRes.stats.updated !== orderIds.length` 只打印 warn，没有返回具体哪些失败。建议返回 `partialSuccess` 信息，前端可以提示。<br><br>E. `importOrders` 中 `mode === 'append'` 时去重只查"最近一天"，但如果导入的是历史数据（非今天），去重逻辑不会生效。这是设计如此，但需要确认是否符合预期。<br><br>F. `importFromXlsx` 代码需要确认是否处理了 `isLastBatch`。<br><br>G. **`_updateOrdersTimestamp` + `_updateDataTimestamp` 冗余 DB 操作** — 每个函数都先 `doc(GROUP_ID).get()` 检查存在再 `doc(GROUP_ID).update()`，单独调用 = 2 次 DB 操作。当 `updateOrder` 中连续调用 `_updateDataTimestamp()` + `_updateOrdersTimestamp()` 时 = 4 次 DB 操作。而 `_touchAllTimestamps` 只需 2 次（1 次 get + 1 次多字段 update）。建议：① 合并为统一的 `_touchTimestamps(fields)` 函数；② 去掉冗余的存在性检查（`initGroup` 后文档必存在），直接 `update` + `catch` 即可。<br><br>H. **`cancelMyOrder` 未触发月度统计重建** — 成员取消自己的 pending 订单后只调了 `_updateOrdersTimestamp()`，但 `getMonthSummary` 的 aggregate 统计的是 `status: neq(CANCELLED)`，取消后月度汇总数据已不准确。虽然 `ordersTimestamp` 更新会触发首页 `checkFreshness` → `refreshMonthSummary`，但 `refreshMonthSummary` 调用的 `getMonthSummary` 依赖 `dataTimestamp` 判断是否需要重建，而 `dataTimestamp` 没有被更新。这意味着月度统计要到下次有价格变动（触发 `_updateDataTimestamp`）时才会被修正。建议 `cancelMyOrder` 也调用 `_updateDataTimestamp()` 或直接 `doRebuildMonthStats`。<br><br>I. **`importOrders`（前端批量导入）与 `_importOrdersFromRows`（CSV/XLSX 导入）代码重复** — 两处实现了几乎相同的订单导入逻辑（去重、分批插入、时间戳更新），只是数据来源不同。建议提取公共的 `_doImportOrders(rows, mode)` 函数，两个入口都调用它。 |
| 好处 | 安全/功能 — 时区一致性；功能 — 批量确认部分失败反馈；功能 — 一天多点限制；**云函数调用 — 合并时间戳更新减少 2 次 DB 操作**；**数据一致性 — 取消订单后月度统计及时修正**；**代码简化 — 消除导入逻辑重复** |

### 6.3 lunch_backup（备份恢复）| 有提升空间

| 项目 | 说明 |
|------|------|
| 设计意图 | 自动/手动备份、恢复、全量导出、清空数据 |
| 改善方案 | A. `restoreBackup` 中先删除所有数据再分批插入，但没有事务保护。如果恢复中途失败，数据可能只剩一半。建议先写入备份数据到临时集合，验证完整后再切换，或至少记录恢复状态。<br><br>B. `clearAllData` 只删 orders/menu/members（保留 creator），但没有清 `lunch_monthly_stats` 和 `lunch_user_menu_stats`。这两个集合的数据会变成孤儿数据，统计页可能显示错误。建议一并清空或重建。<br><br>C. `doBackup` 中 `data: JSON.stringify({ orders, menu, members })` 全部序列化到一个字段，如果数据量大（>10MB）可能超过单文档 16MB 限制。当前 4000 条订单安全，但长期增长需关注。建议备份数据存云存储而非数据库文档。<br><br>D. **`restoreBackup` 恢复后未更新 `lunch_groups` 时间戳** — 删除旧数据并插入新数据后，`ordersTimestamp`、`menuTimestamp`、`membersTimestamp`、`dataTimestamp` 全部是旧值。其他客户端的 `checkFreshness` 比对时间戳不会发现变化，导致看到的是恢复前的缓存数据。建议恢复完成后调用 `_touchAllTimestamps()` 更新所有时间戳。<br><br>E. **`clearAllData` 清空后未更新时间戳** — 同 D，清空数据后时间戳未变，其他客户端无法感知数据已清空。<br><br>F. **`restoreBackup` 剥离 `_id` 导致关联断裂** — 恢复时 `const { _id, ...rest } = o` 剥离了原始 `_id`，所有记录获得新 `_id`。但订单的 `memberId`、`menuId` 引用的是旧 `_id`，恢复后这些引用全部失效。`lunch_order` 中有 `rebuildOrderRelations` 可以修复，但恢复流程没有自动调用。建议恢复完成后自动触发 `rebuildOrderRelations`，或在恢复时保留原始 `_id`（使用 `doc(_id).set()` 代替 `add()`）。<br><br>G. **`restoreBackup` 未清空 `lunch_monthly_stats` 和 `lunch_user_menu_stats`** — 恢复只处理了 orders/menu/members 三个集合，统计集合仍保留旧数据，可能导致统计页显示错误。建议恢复时一并清空这两个集合，恢复后由 `doRebuildMonthStats` 重建。 |
| 好处 | 安全 — 恢复失败不会半残；功能 — 清空数据彻底；安全 — 大数据量备份不超限；**功能修复 — 恢复后其他客户端能感知变化**；**功能修复 — 恢复后订单关联不断裂**；**数据一致性 — 统计集合与订单数据同步** |

## 总结

| 类别 | 数量 |
|------|------|
| 没问题 | 15 个模组 |
| 有提升空间 | 10 个模组 |
| **总计审查** | **25 个模组** |

**核心风险点（建议优先处理）：**
1. `useRealtimeWatch.ts` 硬编码 `GROUP_ID` — 通用模式失效
2. **`lunch_backup` `restoreBackup` 恢复后时间戳未更新 + `_id` 关联断裂** — 其他客户端无法感知恢复，且订单引用全部失效
3. 统计页 `loadStats()` 缺少 `forceRefresh` — 增量/全量逻辑错误
4. 时区一致性 — 多处用 `new Date()` 本地时间
5. 管理页 `startRealtimeWatch` 效率低 — 每次变更全量 `loadData()` 而非本地 patch
6. `cancelMyOrder` 未更新 `dataTimestamp` — 月度统计在取消后不会及时修正
