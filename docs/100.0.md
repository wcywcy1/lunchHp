## 三、新发现：Bug 与风险

### R1（中等）恢复期间 `getRecentOrders` 绕过维护锁执行写操作

**问题**：`getRecentOrders` 被列入 `lunch_order` 的 `READ_ACTIONS`，`exports.main` 对其跳过 `requestGate.enter`（不检查 `restoreJob`）。但它内部第一步就调用 `_autoCancelExpiredPending()`，后者是**写操作**——取消过期 `pending` 订单 + `doRebuildMonthStats` + `_touchTimestamps`。

**后果**：恢复备份期间（`lunch_groups.restoreJob` 存在），维护锁本应让该组织所有写请求返回 423。但普通成员/非发起者管理员进入管理页触发 `getRecentOrders` 时，会绕过租约执行 autoCancel 写，与恢复事务并发写 `lunch_orders` / `lunch_monthly_stats` / `lunch_groups`，可能破坏恢复一致性。

**缓解因素**：autoCancel 有 60 秒实例级节流（`autoCancelByGroup`），且首页 freshness 走 `getDataTimestamps`（不写）→ 恢复期间 `ordersTimestamp` 未变时首页不会触发 `getRecentOrders`。实际风险窗口较窄：主要在"恢复进行中、非发起者的管理员进入管理页"时出现。

**建议**：把 `_autoCancelExpiredPending()` 从 `getRecentOrders` 读路径移出（与 `technical-debt.md` 3.4 的候选优化一致，但此处强调**正确性**而非性能），或在调用前判断 `group.restoreJob` 存在则跳过写。此为上线后首个应处理的点。

### R2（低）`updateOrder` 缺少价格有效性校验

**问题**：`updateOrder` 中 `if (price !== undefined) update.price = Number(price)`，未校验 `Number.isFinite` 或非负。管理员可改出负数或 `NaN` 价格，随后 `doRebuildMonthStats` 会把非法值写入月度统计。

**影响**：目前前端无改价入口（`src/` 未调用 `updateOrder`），属保留接口；但接口本身不安全。

**建议**：与 `submitOrder` 的价格校验对齐（`Number.isFinite` + `>= 0`），一行即可补上。

### R3（低）个人点餐统计查询未分页

**问题**：`getMenuList` / `getInitData` / `_mergeUserStats` 读取 `lunch_user_menu_stats` 时用 `.where({ groupId, memberId }).get()` 未设 `limit`，受云端默认 100 条截断。单个成员点过的菜超过 100 种时，"最近点过"排序会缺数据。

**影响**：20 人团队菜单通常 <100，实际触发概率低；纯展示排序问题，不影响金额统计。

**建议**：数据量接近上限前，按 `fetchAll` 模式补齐（与菜单/成员已修复的方式一致）。

### R4（需实测确认）`searchOrders` 月份筛选的正则 `_.in`

**问题**：`searchOrders` 在传了 `months` 数组时构造 `where.date = _.in(patterns.map(p => db.RegExp({regexp: p})))`，即对正则数组做 `in` 匹配。

**说明**：此处**不套用**"正则必不走索引"的结论（该结论针对带 `options:'i'` 的场景，这里无 `i`），是否影响索引需以云函数日志实测为准。

**建议**：统计页多月份筛选频繁使用且观察到慢查询时，再评估改用 `or` 前缀字符串匹配或单月循环。

### R5（中）语音点餐 `RecorderManager` 占用未释放 → "录音占用"，再次点击无法使用

**现象**：点语音开始→结束后，再次点击语音按钮报"录音占用 / recorder is used"类错误，语音点餐功能无法继续使用（需重启小程序才恢复）。

**根因**：`resetAllStatus()` 只复位前端状态，**没有调用 `recorderManager.stop()`**。状态虽回到 `idle`，底层录音却可能仍在进行，麦克风持续被占用。

**触发路径**（均为 `resetAllStatus()` 被调用、但录音可能仍在录的场景）：

- `startTimeout` 2 秒兜底：`onStart` 未及时触发即复位，但录音可能实际已启动（安卓 `onStart` 延迟/丢失常见）。
- `recorderManager.onError`：录音出错直接复位，未 stop。
- 识别中切页/切后台：`menu/index.vue` 与 `voiceSearch.ts` 均无 `onHide`/`onUnload` 停止录音，录音残留占用。

**相关缺陷**（同一模块，随本次一并记录，前一轮审查已发现）：

1. `start()` 状态锁定过晚：`state.value = 'recording'` 在 `uni.getSetting` 异步回调的 `doStart()` 里才置，双击会进两次 `start()`、两次 `manager.start()`，第二次必报占用。
2. `onStop` 未重置 `pendingStop`、未判空 `tempFilePath`（family-ledger 已做：`pendingStop = false; if (tempFilePath) ... else reset`）。
3. `stop()` 把状态置为 `recognizing` 后，到 `onStop` 回调之间无超时兜底；`onStop` 偶发丢失时停在"识别中"。
4. 识别请求无真正取消：15s `recognizeTimeout` 只复位 UI，迟到的 `callFunction` 结果仍会执行 `onStop` 打断新操作。
5. 云函数 `lunch_voice` 的 `SentenceRecognition` 无超时（Flash 有 1s `Promise.race`，Sentence 无），兜底接口慢时放大挂起窗口。

**建议**（集中在 `voiceSearch.ts`，一处为主）：

- P0：`resetAllStatus()` 开头补 `if (recorderManager && state.value === 'recording') { try { recorderManager.stop() } catch(e){} }`，让所有复位路径统一真正释放占用。
- P0：`start()` 入口立即锁定 `state.value`，防双击重复 start；`authorize`/`getSetting` 失败时走 `resetAllStatus()`。
- P1：菜单页 `onHide`/`onUnload` 停止录音，切页即释放。
- P1：`onStop` 对齐 family-ledger（重置 `pendingStop` + 判空 `tempFilePath`）。
- P2：识别加 `cancelled` 标志/generation，忽略迟到结果。
- P2：`SentenceRecognition` 加 `Promise.race` 超时。

**定位**：`src/utils/voiceSearch.ts`（主）、`wxcloud/functions/lunch_voice/index.js`（Sentence 超时）、`src/pages/menu/index.vue`（onHide 释放）。
